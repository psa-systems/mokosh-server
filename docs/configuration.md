# Configuration

Every value the server reads comes from the configuration provider, and the only provider today is the process environment (see [`providers.md`](providers.md)). `.env` is generated once per clone from the committed `.env.example` by the first `just dev`, minting fresh random values for every self-owned secret; see step 3 of [`quickstart.md`](quickstart.md) for what generation does and does not fill in.

`.env.example` is the complete inventory of keys, not this page: `just check-env-example` fails the build when a key declared in `src/config/registry.rs`, or read directly by one of the entry points, has no `.env.example` key or no `compose.dev.yml` line, and when `.env.example` declares a key nothing consumes. The table below is the annotated subset a developer touches most, with the one column that matters, where the value is actually set.

| Variable | Where set | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `.env` for host-side tools, `compose.dev.yml` for the container | Host-side connection string against the bundled `postgres` service, used by `sqlx migrate` and anything else run on the host. The `server` container gets its own value, composed from the knobs below, connecting as `mokosh_migrator`. |
| `MOKOSH_PG_DB`, `MOKOSH_PG_USER`, `MOKOSH_PG_PASSWORD` | `.env` | Database name, and the superuser the `postgres` service is initialized with. The password is generated per clone on first `.env` creation. |
| `MOKOSH_MIGRATOR_PASSWORD`, `MOKOSH_APP_PASSWORD`, `MOKOSH_APP_DATABASE_URL`, `MOKOSH_ADMIN_DATABASE_URL` | `.env` | The split-role model that makes row-level security enforce at runtime. The server self-provisions two roles at startup: `mokosh_migrator` (`BYPASSRLS`, what `DATABASE_URL` connects as, for migrations, bootstrap and cross-tenant workers) and `mokosh_app` (`NOBYPASSRLS`, what `MOKOSH_APP_DATABASE_URL` connects as, for request serving). `MOKOSH_ADMIN_DATABASE_URL` is the privileged connection used once to create both roles, and is unused after that. With `MOKOSH_APP_DATABASE_URL` unset the server falls back to `DATABASE_URL`, single-role, and row-level security goes inert, so set it in any shared environment. Both passwords are generated per clone. |
| `MOKOSH_PG_HOST_PORT` | `.env` | Loopback port the `postgres` service is published on. Default `5433`. It is the one place that port is written: `DATABASE_URL`, `MOKOSH_ADMIN_DATABASE_URL` and `MOKOSH_APP_DATABASE_URL` interpolate it (PMS-1376), so moving it moves every host-side connection with it. A URL left behind on the old port does not fail on a shared host, it reaches another checkout's database. |
| `MOKOSH_MAILPIT_SMTP_HOST_PORT`, `MOKOSH_MAILPIT_WEB_HOST_PORT`, `MOKOSH_INFISICAL_HOST_PORT`, `MOKOSH_MINIO_API_HOST_PORT`, `MOKOSH_MINIO_CONSOLE_HOST_PORT` | `.env` | The rest of the dev stack's loopback host ports (PMS-900). Defaults `1025`, `8025`, `28002`, `29000`, `29001`. Each is the HOST side only, so the container-side port never moves and nothing in-network changes with them. They exist because two checkouts on one box each publish the same services and the second `just dev` would otherwise fail to bind. Changing `MOKOSH_INFISICAL_HOST_PORT` means changing `INFISICAL_URL` and `INFISICAL_SITE_URL` to match. |
| `MOKOSH_PORT` | `.env` | Port the API server listens on inside its container, and the port Traefik forwards to. Default `8080`. |
| `USER` | written to `.env` by `just dev` | Your username. It names the per-developer containers, volumes, networks and the `${USER}-mokosh-api.a8n.run` route. No service publishes a host port on a LAN address; postgres and mailpit publish on loopback and the server is reached through Traefik (PMS-496, PMS-863). |
| `MOKOSH_SERVER_INFISICAL_ADDRESS` | written to `.env` by `just dev-infisical` | In-network Infisical URL handed to the server as `INFISICAL_ADDRESS`. Empty on a plain `just dev`, which makes the readiness probe report Infisical as `skipped`. |
| `JWT_SECRET`, `ENCRYPTION_KEY` | `.env` | API server secrets, generated per clone on first `.env` creation; provision them explicitly for any non-local environment. `ENCRYPTION_KEY` is also the key the database secret backend encrypts under, so losing it loses every stored secret. |
| `SECRET_BACKEND` | `.env` | Where tenant-supplied secrets live: `database` (the default, AES-256-GCM ciphertext under `ENCRYPTION_KEY`) or `infisical`, which additionally requires `INFISICAL_ADDRESS`, `INFISICAL_PROJECT_ID`, `INFISICAL_CLIENT_ID` and `INFISICAL_CLIENT_SECRET`. An unrecognized value fails startup. |
| `CONFIG_BACKEND` | `.env` | Which provider serves configuration values through the SINGLE-provider slot: `environment` (the default) reads them out of this process's environment. It is the only value `CONFIG_BACKEND` itself accepts; `file`, `database` and `bunyip` are reachable through the separate `CONFIG_PROVIDERS` priority list instead (PMS-987), which this table now documents below. An unrecognized value fails startup naming the legal ones. Deliberately not served by the configuration provider itself, because configuration that says where to find configuration cannot live inside what it locates. |
| `CONFIG_PROVIDERS` | `.env` | Comma-separated priority list of configuration providers (e.g. `file,database,environment`). Empty (the default) falls back to the hosting profile's default provider. This is what today powers the `provider-status`, `provider-migrate` and `provider-purge` operator CLI subcommands (PMS-1012); ordinary request-serving configuration reads still go only through the `CONFIG_BACKEND` single-provider slot above. |
| `AUTH_PROVIDERS` | `.env` | Comma-separated authentication-provider priority list. Unset reproduces the hosting profile's default (`bunyip,local` in `saas`, `local` in `self-hosted`). Enforced since PMS-981 landed the gate: `AuthService::login` refuses the local password path when `Local` is excluded, and `auth_middleware` skips the Bunyip-verification branch when `Bunyip` is excluded. |
| `MAIL_PROVIDER` | `.env` | Named email provider selection: `log` (`LogMailer`, no bytes leave the box) or `smtp` (`SmtpMailer` against `SMTP_HOST`). Unset falls back to the hosting profile's default (`log` self-hosted, `smtp` saas), unless `SMTP_HOST` is set with no provider named, which implies `smtp`. An unrecognized value, or `smtp` with no `SMTP_HOST`, fails startup. |
| `ORGANIZATIONS_ENABLED` | `.env` | The organizations feature flag. Unset resolves to the hosting profile's default (off `self-hosted`, on `saas`); set explicitly to override. |
| `LOGIN_APPROVAL_ENABLED` | `.env` | Turns on the suspicious-login notify-and-approve gate. Default `false`/off, since it can withhold a login. |
| `BRANDING_TENANT_FAVICON_MAX_BYTES`, `BRANDING_TENANT_BACKGROUND_MAX_BYTES`, `BRANDING_COMPANY_LOGO_MAX_BYTES`, `BRANDING_COMPANY_FAVICON_MAX_BYTES`, `BRANDING_COMPANY_BACKGROUND_MAX_BYTES` | `.env` | Five of the six per-`(scope, kind)` branding asset caps, in bytes (the sixth, `TENANT_LOGO_MAX_BYTES`, predates this row). Defaults are `BrandAssetKind::default_max_bytes`: 1 MiB for a logo, 512 KiB for a favicon, 2 MiB for a background. |
| `BUNYIP_STATUS_CLIENT_ID`, `BUNYIP_STATUS_CLIENT_SECRET` | `.env` | Machine credential Bunyip's provider-status aggregator presents as HTTP Basic against `GET /api/v1/admin/providers/status`. Both empty (the default) disables the machine-credential path and the route gates on `RequireAdmin` alone. |
| `GOOGLE_CONTACTS_CLIENT_ID`, `GOOGLE_CONTACTS_CLIENT_SECRET` | `.env` | The Google Cloud OAuth client the Google Contacts one-way import connects with. Both unset (the default) disables the integration. |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | `.env` | Optional first-run admin bootstrap, dev only. Both empty in a generated `.env`; see [`first-run-onboarding.md`](first-run-onboarding.md). |
| `INFISICAL_URL` | `.env` | Host-side URL of the dev Infisical instance, read by the bootstrap CLI when `just infisical-bootstrap` runs it on the host. Default `http://localhost:28002`. Not the same key as `MOKOSH_SERVER_INFISICAL_ADDRESS` above, which is the in-network URL the server container gets. |
| `INFISICAL_*` | `.env` | Infisical server config (bootstrap inputs) and Universal Auth client credentials (filled by `mokosh-bootstrap`). |
| `STORAGE_PROVIDER` | `compose.dev.yml` | Which provider stores objects: `local` (the default, and the hosting profile's in both modes) or `s3`. An unrecognized value fails startup rather than falling back, so a typo cannot quietly write uploads to a container filesystem. Renamed from `STORAGE_BACKEND` by PMS-1317, which still works as a deprecated alias. |
| `STORAGE_ROOT` | `compose.dev.yml` | Filesystem root the `local` provider hangs every stored object off: ticket attachments, tenant logos, knowledge base images and issued documents, each under its own tenant (the layout table is in [`architecture.md`](architecture.md)). Left commented out in `.env.example` on purpose: the dev stack points it at `/data/attachments` on the `dev-mokosh-attachments-${USER}` volume so an upload survives a rebuild, and setting it in `.env` would override that. Deployed environments want an absolute path on a mounted volume. Renamed from `ATTACHMENT_DIR` by PMS-1317, which still works as a deprecated alias; the old name described one of the four things kept under that root, which is what made it misleading. |
| `STORAGE_S3_ENDPOINT`, `STORAGE_S3_BUCKET`, `STORAGE_S3_REGION`, `STORAGE_S3_PATH_STYLE`, `STORAGE_S3_ACCESS_KEY_ID`, `STORAGE_S3_SECRET_ACCESS_KEY` | `compose.dev.yml` | The S3-compatible store, read only when `STORAGE_PROVIDER=s3`. Endpoint, bucket and both halves of the credential are required, and a deployment that asks for `s3` without them refuses to boot rather than 500ing on the first upload; the region defaults to `us-east-1` and path-style addressing to `true`, which is what every non-AWS store serves. Renamed from the bare `S3_*` names by PMS-1317, which still work as deprecated aliases. |
| deprecated: `ATTACHMENT_DIR`, `STORAGE_BACKEND`, `S3_*` | `compose.dev.yml` | Honoured for one release, and only when the `STORAGE_`-prefixed name above is unset. Using one logs a line naming its replacement, and `mokosh-server provider-status` reports which name supplied each setting, so finishing the migration is a question with an answer. |
| `RUN_MIGRATIONS` | `.env` | Whether the server applies pending migrations on start. Default `true` whether or not the variable is set. |
| `RUST_LOG` | `.env` | Tracing subscriber filter. |

`compose.dev.yml` references every value via `${VAR}` substitution and contains no hardcoded secrets. Required vars use `${VAR:?...}` so compose fails loudly with a helpful message when a value is missing.
