# Architecture

What mokosh-server is made of: the runtime pieces, where the code lives, how the schema moves, and what ships as an image. Start with [`quickstart.md`](quickstart.md) if you just want the dev stack running.

## Runtime shape

- **HTTP**: Axum 0.8 (Tokio runtime) with Tower middleware (CORS, tracing, brotli/gzip compression, request limits, request-id).
- **Database**: PostgreSQL 18 via SQLx (compile-time-checked migrations).
- **Secrets**: tenant-supplied secrets are AES-256-GCM ciphertext in the database by default, encrypted under `ENCRYPTION_KEY` (`SECRET_BACKEND=database`). `SECRET_BACKEND=infisical` keeps them in a self-hosted Infisical instance reached over HTTP instead, and then also requires `INFISICAL_ADDRESS`, `INFISICAL_PROJECT_ID`, `INFISICAL_CLIENT_ID` and `INFISICAL_CLIENT_SECRET`. An unrecognized value is a startup error rather than a fall back to the default.
- **Email**: Lettre (SMTP).
- **Auth**: two independent mechanisms run in parallel, and failing to mount one does not disable the other. The SPA and the E2E suite authenticate through bunyip, the sole OpenID Connect provider: mokosh verifies bunyip-issued Bearer tokens against bunyip's JWKS, configured by `OIDC_ISSUER` and `OIDC_AUDIENCE`. The original PSA endpoints use the legacy HS256 Bearer-token session with Argon2 password hashing. The [Auth](#auth-two-independent-mechanisms-pms-295) section below carries the detail.
- **Tenancy**: multi-tenant only. Every service method takes an explicit `tenant_id`; the former `single-tenant` cargo feature was removed.

## Modules

Feature modules live under `src/modules/`, one directory each, and cover the usual PSA surface area: tickets, contracts, contacts, billing, quotes, projects, assets, time tracking, SLAs, RMM, knowledge base, portal, reports, notifications, audit, auth, tenants, settings and calendar, among others.

That list is illustrative, not a census: a hand-copied one goes stale within a month and a reader cannot tell. `ls src/modules` is the current set, `src/api/router.rs` is what is actually mounted, and the [Routing model](#routing-model) section below says what authenticates each top-level nest under `/api/v1`.

## Why Traefik ingress, and why loopback for the rest?

The dev host is a VPS on the public internet, and several developers share it. The `server` is reached only through the shared Traefik, which gives each developer their own `*.a8n.run` hostname with a real Let's Encrypt certificate instead of a port on a shared IP. Everything else that needs a host port (`postgres` for `sqlx-cli`, `mailpit` for the mail UI, `infisical` for its admin UI) publishes on `127.0.0.1` only, so it is reachable from the host's own tooling and from nowhere else. Sibling containers do not need a host port either: they reach each service by its compose DNS name on the `dev-mokosh-private-${USER}` network.

## Stored file layout

Every stored object is addressed by an `ObjectKey`: a tenant plus the object's identity, never a path. A caller cannot assemble one, so the layout is decided in exactly one file (`src/storage/mod.rs`) and pinned by a test there, because getting an arm wrong does not fail loudly - it serves a 404 for a file that is still sitting on disk.

Under the storage root (`STORAGE_ROOT` for `local`, the bucket for `s3`, same string either way):

| Path | What it is |
|---|---|
| `{tenant}/{id}` | ticket attachment |
| `{tenant}/logo.{ext}` | the tenant's live logo, overwritten on replace |
| `{tenant}/kb-articles/{id}` | image embedded in a KB article |
| `{tenant}/documents/{id}` | issued invoice or credit-note PDF |
| `{tenant}/branding/{digest}` | a logo frozen onto a sent invoice, content-addressed |
| `{tenant}/contact-imports/{id}` | an uploaded `.vcf`, held until the import that reads it ends |

Two of these arrived at that shape late, and both moved the same way. A KB attachment was a flat `kb-articles/{id}` with no tenant anywhere in it (PMS-960); the live logo was `tenant-logos/{tenant}.{ext}`, a shared directory with the tenant in the filename. Each old path stays addressable as its own `ObjectKind::Legacy*` variant rather than as a fallback inside the provider - a fallback applies to every read and is reachable from any tenant's key, which is the hole being closed - the read falls back to it so nothing disappears mid-deploy, and a one-shot (`KbAttachmentMover`, `TenantLogoMover`, spawned once per process start by `scheduler::one_shot::spawn_once`) walks the files over. They were `Scheduler` jobs at an hour until PMS-1320, which is a recurring job doing a one-time correction; a migration is not available for either, because what moves is bytes in `crate::storage` and a migration runs inside Postgres. Each mover moves the file first and updates the `files` ledger row second, because a row naming a path before the bytes are there is the one ordering that can lie, and it leaves an object whose bytes are at neither path completely alone.

`{tenant}/logo.{ext}` and `{tenant}/branding/{digest}` are deliberately not the same directory: the first is one mutable object per tenant, the second is the content-addressed copies frozen onto documents, one per distinct logo rather than one per invoice.

Five paths are NOT in that table and do not begin with their tenant, which PMS-1318 enumerated and PMS-1397 closes: `tenant-favicons/{tenant}.{ext}`, `tenant-backgrounds/{tenant}.{ext}`, `company-logos/{company}.{ext}`, `company-favicons/{company}.{ext}` and `company-backgrounds/{company}.{ext}`. They are written by `BrandingAssetStore` (`src/modules/branding/assets.rs`), the one writer of the upload root outside this seam, and only its `(Tenant, Logo)` pair goes through `ObjectKey` - which is why the logo moved under its tenant and its five siblings did not. No tenant reads another's through the API, because the routes that serve them are deliberately public with the id as the credential and no tenant-scoped key is presented; what is missing is the prefix a per-tenant bucket, quota or export would be built on. `branding::assets::tests::the_unscoped_pairs_are_the_ones_pms_1318_found` holds the list, so a sixth pair on that layout fails rather than joining them quietly, and `storage::tests::every_object_kind_puts_its_tenant_first` is the corresponding property for everything that does go through `ObjectKey`, with the two `Legacy*` read paths as its only named exceptions.

## Database migrations

Migrations live in `migrations/` and are embedded into the binary at compile time via `sqlx::migrate!`. They run automatically on server start when `RUN_MIGRATIONS=true`, which is the default whether or not the variable is set.

```nu
# Apply pending migrations against $DATABASE_URL (host-side).
just migrate-run

# Create a new migration.
just migrate-create add_widgets_table
```

Compile-time migration validation requires the `migrations/` directory to be present at build time. Both the dev `Dockerfile` and `oci-build/Dockerfile` copy it into the image.

A migration already on `main` is immutable: SQLx re-verifies applied-migration checksums on boot, so editing one stops every deployed database. `just check-migration-immutability` is the guard.

## Releases

`just create-release <major|minor|hotfix>` bumps the version in `Cargo.toml`, syncs `Cargo.lock`, creates and pushes a `release/v<X.Y.Z>` branch, and prints the PR URL. After the PR merges, the `create-release` workflow tags and publishes the release automatically.

Both halves come from `psa-systems/common` since PMS-786: the recipe is imported from the `common` submodule (`release_layout` stays `"generic"`, the version living at the root `[package] version`), and `.forgejo/workflows/create-release.yml` is a thin caller of common's reusable workflow, so the release-notes format is shared with every other consumer rather than forked here. The notes are one line per merged pull request, grouped by conventional-commit type; the previous private copy listed every commit, which double-reported each PR.

## Auth: two independent mechanisms (PMS-295)

bunyip-as-OP is the only OP. PMS-295 removed mokosh-auth (mechanism 2, mokosh's own OIDC OP) entirely; the server now accepts two independent auth paths in parallel, and failing to mount one does NOT disable the other:

1. **Bunyip-as-OP Resource-Server** (`src/modules/auth/oidc_rs.rs`): mokosh verifies bunyip-issued `at+jwt` Bearer tokens against bunyip's JWKS. Configured by `OIDC_ISSUER` + `OIDC_AUDIENCE`. This is the path the mokosh-apps SPA and the E2E suite actually use; tokens come from `api.<tld>` = bunyip. Mokosh holds no signing key and exposes no `/oauth2/*` endpoints.
2. **Legacy HS256 Bearer auth** (`src/modules/auth/`): JWT in an `Authorization: Bearer` header, Argon2 password hashing, session rows in `user_sessions`. Used by the original PSA endpoints. `AuthMiddleware` decodes the Bearer token into an `AuthState`. Routes opt in via `RequireAuth` / `RequireRole` / `RequireAdmin` / `RequireManager` / `RequireFinance` extractors. TOTP (RFC 6238) + MFA recovery codes for this path live in `src/utils/totp.rs` + `src/utils/recovery.rs` (relocated from the removed `mokosh-auth-crypto` crate in PMS-295).

Both paths run the same principal gate (PMS-698): `AuthService::ensure_principal_usable` rejects a `users.status != 'active'` row and a tenant whose `status != 'active'`, so deactivating a user or suspending a tenant takes effect on the very next request regardless of which mechanism minted the token. On the bunyip path the gate runs in `resolve_bunyip_caller` on the row as it was read, BEFORE any placement decision (PMS-1125): the PMS-245 default-tenant backfill and an invite both re-home the user, and the backfill provisions a personal tenant first, so a gate that ran after them let a refused request move the row and left the legacy token 404ing on its old tenant. The refusal also rides out of the PMS-777 local-state path as the second half of `LocalPlacement::Placed`; that path used to keep only the state, which is why an inactive user in a real tenant (the everyday shape) got a bare 401 and the log showed only the legacy decoder's false `JWT error: InvalidAlgorithm` line for the EdDSA header. `auth_middleware` no longer runs the legacy decoder on a bearer the bunyip verifier accepted, and warns once, naming the sub, when a verified bearer yields no principal and no refusal was carried. The PMS-681 `iat`-vs-`password_changed_at` cutoff stays legacy-only on purpose: bunyip owns the credential on path 1, so a mokosh-side password change is not a revocation signal there. So does the MAPPS-531 session check, for the same reason: every legacy access token names a `user_sessions` row in its `sid`, and `ensure_user_and_tenant_active` refuses the request once that row is gone, so a sign-out revokes the access token and not just the refresh. That is why sign-out is a DELETE here where the portal (below) needs a stamp, and why `POST /api/v1/auth/logout-all` (PMS-880, audit F3) needs no cutoff column of its own: deleting every row for the user fails the same check for every token they hold.

A caller's OWN tenant is resolved from Mokosh's membership state, never from a token claim (PMS-244, confirmed again under PMS-901). Bunyip is a personal-subscription IdP with no org concept, so orgs live here: `ensure_user_from_bunyip` picks the tenant by a pending invite for the verified email, else the user's existing placement, else a brand-new `personal` tenant on self-signup. Migration 034 added a `tenants.bunyip_org_id` for the claim-based approach and migration 036 dropped it again; nothing in Rust has read it since, and rebuilding that mapping is the thing this rule exists to prevent.

The three `mokosh_grant_*` claims are not a counter-example, and they are what makes the rule worth writing down, because `mokosh_grant_account_id` carries a Mokosh tenant SLUG and reads exactly like the join key PMS-896 assumed (BUNYIP-673/674). It names a DELEGATED target rather than the caller's own tenancy: `resolve_bunyip_caller` routes such a token to `resolve_grantee_caller` instead of the owner path, and the slug means nothing until it is checked against the locally mirrored `mokosh_account_grants` row and the target tenant's own placement. So a claim can still only name a tenant that local state already authorises, and a token cannot assert a tenancy into existence. A future change that wants an identity's home tenant to come from a claim is a new design with its own precedence rule against the invite / placement / personal-tenant ladder, not an extension of these.

**History (PMS-291 / PMS-292 / PMS-289)**: mokosh-auth was a configured-but-unused second IdP (`crates/mokosh-auth*`). PMS-289 made a misconfigured mokosh-auth a fatal boot error, which took staging+prod down (PMS-292 restored service by provisioning keys - interim path B). PMS-295 is the path-A follow-up: tear mokosh-auth out so `MOKOSH_AUTH_*` env, the `crates/mokosh-auth*` workspace members, and the `mokosh-server-secrets` volume all go away. The server boots fine with no `MOKOSH_AUTH_*` env present.

PMS-837 removed the last auth-adjacent workspace crate: `google-oauth-flow` and the `/api/v1/auth/google` + `/api/v1/auth/google/callback` popup routes it served went away with the `GOOGLE_OAUTH_*` and `OAUTH_SUPER_ADMIN_EMAILS` env vars. No client ever called them (three parity audits between 2026-07-30 and 2026-08-14 found the routes unconsumed, and mokosh-apps still has no reference). `google_oauth_routes_stay_unmounted` in `src/modules/auth/routes.rs` is the guard that fails if either mount returns; the `user_oauth_identities` table stays, because migrations are immutable.

## The contact plane is a third, fully separate identity plane

A contact identity is a `contacts` row (`portal_password_hash`, `is_portal_user`); a platform identity is a `users` row. One email address can legitimately hold one platform account and a contact identity in several tenants at once, so the contact plane owns its whole credential lifecycle: `POST /api/v1/contact/auth/{login,setup-password}` resolve the identity from `contacts` inside the tenant named by the request path and never read or write `users`. `/api/v1/auth/forgot-password` is the platform path and resolves against `users` only; an address that is contact-only finds no user there and gets the same silent 200 as any unknown address. Do NOT point the contact plane at the platform reset endpoints: one credential path serving two identity kinds was the defect, where a customer resetting their contact-plane password reset a staff login instead.

A portal password reset goes through the MSP, and there is no self-service half (PMS-1343): a contact who has lost their password asks their provider, an agent reissues the link from the contact record with `POST /api/v1/contacts/contacts/{id}/resend-portal-invite`, and that link redeems on `POST /api/v1/contact/auth/set-password` like a first-time invite. The MSP owns the client relationship, so it owns the credential reset; `revoke-portal-access` beside it is the other half of that ownership, blocking sign-in while preserving the contact record, and a reset is refused for a revoked contact. `POST /api/v1/contact/auth/{forgot-password,reset-password}` are GONE, along with `ContactAuthService::{request_password_reset,reset_password}` and the per-(IP, slug+email) budget that fronted the first: a customer-initiated reset ran `UPDATE portal_setup_tokens SET used_at = NOW()` over every unredeemed row for the contact (PMS-1297, so a new link supersedes the old), which meant a customer clicking "forgot password" silently killed the link their MSP had just sent them and each blamed the other. The redemption token is still the `portal_setup_tokens` row and its `{contact_id}.{secret}` shape (Argon2-hashed, single use, 24h), still rate limited by `AuthRateLimiter` (10/min per IP, 3/min per contact id in the token), and still holds one replay contract: 204, then 410 on replay, 400 on expired/unknown. `auth.portal_password_reset` keeps its seeded `notification_templates` row in every tenant because migrations are immutable, and it now has no dispatch site; so does the `portal.password_reset` audit subtype, and a redemption writes `portal.setup_password` whether it is a first password or a reset.

The stateless model that used to sit here (`PortalAuthService`, `PortalJwtClaims`, `portal_auth_middleware`, the `contacts.portal_tokens_valid_from` cutoff, `POST /api/v1/portal/auth/logout`) has been retired. `ContactAuthService::login` mints a stateful session backed by a `contact_sessions` row and the paragraphs below describe how revocation actually works; the retired symbols are named here only so a search that finds them recognises them as gone.

Contact-plane authorization keys on two tables, not on a single billing-contact bit. `portal_roles` (tenant-wide, or `company_id`-scoped to one Company) defines the role and its capability set, and `contact_role_assignments` links a contact to the roles it holds; the effective set is read from the database on every request through `ContactAuthService::load_capabilities` with no cache, so revoking a role takes effect on the next request rather than the next login. The MSP-side surface is `PortalRoleService` under `/api/v1/portal-roles` and `/api/v1/contacts/companies/{company_id}/portal-roles`, and the capability catalog is `src/modules/contact_portal/capabilities.rs`. The billing contact per company is `companies.default_billing_contact_id`, still per-company and single-valued by construction, still deliberately kept off the JWT so a reassignment takes effect on the next request rather than the next login; `contacts.contact_type = 'billing'` is a classification label and grants nothing, and neither is `RequireBilling`, which is the agent-side module-enable gate.

A contact session on the `/api/v1/contact/*` plane is stateful and belongs to a rotation family (PMS-1062): `contact_sessions.family_id` is the id of the first session in the chain (a login or a magic-link redeem) and every rotation through `POST /contact/auth/refresh` copies it forward, so "the whole chain" is one UPDATE by family rather than a recursive walk. A genuine refresh token presented AFTER it was rotated is the stolen-token signal (the honest customer rotated it, so whoever holds it now holds a copy), and it revokes the family, the customer's current token included; so does `POST /contact/auth/logout`, and so does losing the rotation race. Both paths verify the secret BEFORE revoking anything, because a session id rides in every access token's `sid` and a bare id must not be enough to sign a customer out; a replay with the wrong secret is a plain 401 that revokes nothing. Setting or resetting the password (`setup_password`, the one redemption path since PMS-1343) revokes every open session for the contact in the same transaction as the new hash, so a token stolen before a reset dies with it. Changing it while signed in (`PUT /contact/auth/me/password`, PMS-1086) does the same minus the caller's own family, named by the access token's `sid`, so the device the customer is typing on stays signed in; the current-password re-auth there and on `POST /contact/auth/me/mfa/disable` shares one failure-counted `ReauthRateLimiter` budget (the PMS-881 shape), spent only by a rejected password. `GET /contact/auth/me/sessions` lists the contact's live sessions ONE PER FAMILY (PMS-1085), keyed on `family_id` so the id survives rotation, with `current` on the caller's own; `DELETE /contact/auth/me/sessions/{id}` revokes that family, refuses the caller's own with a 400 that points at logout (the SPA must clear its in-memory token too), and answers an id that is not the caller's with a silent 204, the same enumeration-resistant shape as logout. None of that reached the bearer until PMS-1224: the middleware decoded the JWT and checked only the tenant, so a revoked session's access token still served every contact route until its own 15-minute TTL ran out, and `ContactAuthService::ensure_session_active` is the per-request check that closed it. That check asks the FAMILY and not the one row (PMS-1259), because `revoked_at` carries two meanings: `refresh` stamps it on the row it was handed before minting the successor, which means SUPERSEDED, while every other writer (`revoke_session_family` and its five callers, `set_password_with_token`, `change_password`, `revoke_portal_access`) takes a whole family or every row the contact holds, which means REVOKED. Reading the row alone conflated them and killed a still-unexpired access token the moment its sibling refresh token rotated, so any request the SPA had in flight across a refresh came back 401. A family holding a live row is accepted, a family holding none is refused, and a `sid` naming no row is refused, so every revocation above still kicks the bearer on its next request while an ordinary rotation leaves it serving its own TTL out. Every one of these events writes an `audit_log` row through `audit_portal_event` (PMS-1089): `entity_type = 'portal_contact'`, the contact in `entity_id`, `user_id` NULL because the actor is a `contacts` row and not a `users` row, and the subtype in `new_values.event` (`portal.login`, `portal.login_failed`, `portal.mfa_failed`, `portal.login_link`, `portal.logout`, `portal.refresh_replay_detected`, `portal.refresh_refused_inactive`, `portal.setup_password`, `portal.password_reset`, `portal.password_changed`, `portal.mfa_setup_started`, `portal.mfa_enabled`, `portal.mfa_disabled`, `portal.session_revoked`). The writes are best-effort through `ContactAuthService::audit`: a failed audit write is a warning and never changes the auth response, and the login, magic-link, refresh, logout and session-revoke rows carry the client IP and user agent because those handlers have them.

A contact's second factor is enforced on both login paths and enrolled from the portal (PMS-1063): `ContactAuthService::login` reads `contacts.portal_mfa_enabled` after the password verifies and answers `mfa_required: true` with empty tokens when no code came, verifies `mfa_code` (TOTP, one step of skew) or `recovery_code` (single use, `array_remove` on the hash array, the recovery code winning when both are sent) when one did, and a wrong code ticks `portal_failed_login_count` exactly as a wrong password does, so the PMS-501 lockout throttles a second-factor grinder too. The magic-link redeem gates on the same flag, not on whether a secret is staged, so an abandoned enrolment does not strand the link. Enrolment is `POST /contact/auth/me/mfa/{setup,enable,disable}`, all behind the session AND the current password (a stolen access token must not enrol an attacker's authenticator, finish one it started, or remove the factor); setup stages the secret without flipping the flag and only enable, after a live code verifies, turns it on, so a mis-set authenticator cannot lock the customer out. `portal_mfa_secret` is sealed at rest with the same `auth::mfa_secret` helpers and `ENCRYPTION_KEY` that protect `users.mfa_secret` (PMS-871), a plaintext row from before is read as legacy and rewritten sealed on its next successful verification, and `ContactAuthService::with_encryption_key` is how the router hands the key over. The magic-link redeem completes the same way (PMS-1077): a POST with no code is answered `mfa_required: true` and leaves the intent UNCONSUMED, so the second POST with `{ token, mfa_code }` or `recovery_code` finds the link live; the code goes through the same `verify_second_factor`, a wrong one is a 401 that ticks the counter and leaves the link live (bounded by its expiry and the lockout), and a right one consumes the link inside the locked transaction before anything is minted. Before this the intent was consumed before the gate, so the second POST was refused as a replay. There is no captcha on this plane: the Cloudflare Turnstile keys the retired portal router read left with it (PMS-1090), and what throttles a contact login is the PMS-501 lockout on `portal_failed_login_count` / `portal_locked_until`, which the second factor shares, plus the per-IP and per-email windows on the magic-link request; `AuthRateLimiter` covers no contact endpoint.

## Routing model

`create_api_router` (`src/api/router.rs`) builds these top-level nests, plus a fallback. Each one states what authenticates a request to it; keep this list in step with the `.nest(...)` calls at the end of `create_api_router`.

- `/api/v1/*` PSA router. Every module exposes either `<name>_routes(service)` (nested under a prefix) or merges directly when it owns multiple top-level prefixes (e.g. `time_tracking_routes`, `projects_routes`, `calendar_routes`, `contracts_routes`, `billing_routes`, etc. all use `.merge`). Authenticated by the session: `auth_middleware` runs globally and populates `AuthState`; route handlers opt in via `RequireAuth` / `RequireRole` / `RequireAdmin` / `RequireManager` / `RequireFinance`.
- `/api/v1/public/*` UNAUTHENTICATED, by design. Nothing authenticates a request to this subtree: no session, no cookie, no bearer, no signature. Everything it serves is listed here. `GET` and `POST /api/v1/public/request-forms/{token}` (`src/modules/forms/public_routes.rs`), where the single-use magic-link token in the URL is the only identity and resolves its own tenant, throttled per client IP by `RequestFormLimiter`. `GET /api/v1/public/tenants/{tenant_id}/logo` (`src/modules/tenants/routes.rs`), which a recipient's mail client fetches straight out of a request-form email and can never authenticate; a tenant with no logo 404s identically to a tenant id that does not exist, and SVG is excluded from the allowed upload types. All three image routes here share one allowlist, `utils::inline_image::check_inline_image_mime`, guarded by a single-definition test the way `utils::net` guards `is_non_public_ip`: they make the same bargain, so they must refuse the same types (PMS-941). `GET /api/v1/public/kb/attachments/{attachment_id}` (`src/modules/knowledge_base/attachments.rs`), an image embedded in a KB article, where the attachment's v4 UUID is the only credential: a browser fetches it as `<img src>`, an `<img>` carries no `Authorization` header, and the SPA holds a bearer rather than a cookie, so there is no authenticated form of this request to make. The cost is real and deliberate: anyone holding the URL can fetch the image even for an `internal` or `client_specific` article. An unknown id and a deleted attachment 404 identically so it is not an existence oracle, SVG is excluded for the same reason as the logo, and the read runs on the migrator pool with a SAFETY note because it has no tenant context to set (PMS-923). `GET /api/v1/public/tickets/attachments/{attachment_id}` (`src/modules/tickets/attachments.rs`), an image embedded in a ticket description or note, for the same `<img>` reason and with one extra guard (PMS-941): `ticket_attachments` has no MIME allowlist and already holds portal uploads and PMS-450 inbound-email attachments, all stored under an authenticated-only contract, so the read serves ONLY rows carrying `is_inline` and that flag is set by nothing but `AttachmentService::create_inline` (image-only via `utils::inline_image`, `note_id` NULL, capped at 5 MiB). A real-but-unflagged attachment 404s exactly as an unknown id does, because the flag is in the WHERE clause rather than a check after the fetch. `GET /api/v1/public/contact-sync/google/callback` (`src/modules/contact_sync/routes.rs`), the OAuth redirect Google sends an admin's browser to after they consent (PMS-1212): a redirect carries no session, so the credential is the single-use `state` parameter, which is the `{id}.{secret}` setup-token shape (migration 221, Argon2-hashed, ten minutes, consumed before the token exchange so a slow exchange cannot be replayed). It exposes nothing either way - every outcome, including a refusal, is a redirect back to the SPA carrying a flag and never the provider's text. A handler added here answers anyone on the internet: it needs its own throttle and must expose nothing that a tenant id or a leaked token alone should not unlock.
- `/api/v1/contact/*` contact router with its OWN auth middleware (identity = `contacts` row, not `users`). Authenticated by an `at+jwt` Bearer that `portal_contact_middleware` decodes and `RequireContactAuth` extracts; `contact_routes` is what `crate::modules::contact_portal::contact_routes` mounts, and its surface is the credential lifecycle (`/contact/auth/{login,setup-password}`, rate limited by `AuthRateLimiter` and reachable without a bearer), sign-out (`POST /contact/auth/logout`), session listing and per-session revoke (`GET /contact/auth/me/sessions`, `DELETE /contact/auth/me/sessions/{id}`), the password change (`PUT /contact/auth/me/password`), the MFA enrolment triple (`POST /contact/auth/me/mfa/{setup,enable,disable}`), and the magic-link flow (`POST /contact/auth/login-link/{request,redeem}`). The dual-plane surfaces staff and contacts BOTH read (invoices, tickets, portal roles, KB read) live under `/api/v1/*` and gate on `RequireCallerContext`, which resolves the caller once and dispatches to a staff branch or a contact branch, with the contact branch consulting `caps::*` on the effective role set; the older `/api/v1/portal/*` mount, `PortalAuthService`, `PortalJwtClaims`, `portal_auth_middleware`, `RequirePortalAuth` and `RequirePortalBillingContact` are retired and are named here only so a search finds them tagged as gone. Never sees `AuthState`.
- `/api/v1/bunyip/*` bunyip receivers, none of them session-authenticated. `POST /webhooks/account-deleted` (PMS-591) and `POST /webhooks/mokosh-grant-changed` (BUNYIP-674) are authenticated by the `X-Webhook-Signature` HMAC-SHA256 over the body, keyed by `BUNYIP_WEBHOOK_SECRET`. `POST /oauth2/backchannel-logout` (PMS-998) is authenticated by the logout token itself: a form-encoded `logout_token`, signed by the OP and verified through the same JWKS the `at+jwt` path uses, so it needs no shared secret of its own. Two things about it are easy to get wrong. Its `aud` is the OIDC CLIENT id and not `OIDC_AUDIENCE`, which is the resource-server audience on the access token, so it is checked against `OIDC_BACKCHANNEL_CLIENT_ID` and the receiver refuses everything while that is unset (with no client id it cannot tell a token addressed to this deployment from one addressed to another client of the same OP). And a logout token carries no `exp`, so freshness is an `iat` window instead; without one, a captured token would revoke its session on every replay, forever. A verified token's `sid` goes into an in-memory, TTL-bounded set that `auth_middleware` consults on the bunyip bearer path, so a session the OP ended is refused on the next request rather than at the access token's expiry, with its own `WWW-Authenticate` description so a client can tell it from a plain expiry. A token carrying no `sid` is unaffected, which is every token minted before BUNYIP-636.
- `/api/v1/stripe/*` Stripe webhook receiver (`POST /webhooks/{tenant_id}`). Authenticated by the `Stripe-Signature` HMAC over the raw body, keyed by that tenant's stored webhook signing secret (PMS-711), not by a session. The tenant id in the path selects which secret to verify against; it is not itself a credential.
- `/api/v1/paypal/*` PayPal webhook receiver (`POST /webhooks/{tenant_id}`), the same `provider_webhook_handler` as Stripe's mounted with `provider_id: "paypal"` (PMS-969). Authenticated by the five `PAYPAL-TRANSMISSION-*` headers, which the provider does not check locally: PayPal signs RSA-SHA256 against a certificate served at a URL in those headers, so the supported path is `POST /v1/notifications/verify-webhook-signature`, sending the headers and body back to PayPal for a SUCCESS or FAILURE. That call is why the prefix is in `RAW_BODY_PATHS` despite not being an HMAC: a byte the sanitizer rewrote is a FAILURE there. The receiver refuses a delivery whose resolved provider is not the one the route names, so a late Stripe delivery to a tenant now on PayPal is a 401 rather than a mis-verified body. PayPal also does not charge on approval; `CHECKOUT.ORDER.APPROVED` is `PaymentEvent::RequiresCapture`, the receiver calls `PaymentProvider::capture`, and the resulting `PAYMENT.CAPTURE.COMPLETED` records the payment.
- Fallback for non-API paths: small HTML "not a frontend" page linking back to the SaaS shell. No authentication; it renders the same page for anyone.

`#[cfg(feature = "multi-tenant")]` gates the `/tenants` CRUD routes; default features are `["multi-tenant", "server"]`. The `server` feature gates HTTP-only code so the library crate can be reused without Axum.

Every JSON request body to every one of those trees passes through `utils::text::sanitize_json_body` (PMS-924) before any extractor sees it: it strips the `Cf` format characters and U+00AD, folds non-ASCII whitespace to a plain space, and trims, at every depth including object keys. A handler therefore never sees `Acme\u{200B}`, and no route can forget to opt in the way a `SanitizedJson<T>` extractor on 156 `Json<T>` handlers would. Two carve-outs, both enforced in that module and both tested. **Secrets** are exempt by field name (`SECRET_FIELD_NAMES`): a password, token, API key or webhook secret is compared byte for byte against something stored elsewhere, so rewriting one is a failed login with nothing in the log. **Signature-verified receivers** are exempt by path (`RAW_BODY_PATHS`: the Bunyip, Stripe and PayPal webhooks, `POST /api/v1/rmm/alerts`), because each verifies the raw bytes (three by HMAC, PayPal by sending them back) and a one-byte rewrite is a 401. Adding a fifth verify-over-body route means adding its `RAW_BODY_PATHS` prefix in the same change. Non-JSON bodies (multipart uploads, attachments) are forwarded byte-identical and never buffered.

## Migration rules

Per-feature files under `migrations/` (split from the original `001_initial_schema.sql` monolith in PMS-128). Embedded at compile time via `sqlx::migrate!`; `migrations/` must exist in the build context (both Dockerfiles copy it). On server start with `RUN_MIGRATIONS=true` (default) migrations run automatically.

**Migrations are immutable once committed.** sqlx stores a SHA-384 checksum of each migration in `_sqlx_migrations` when it applies it, and re-verifies on every startup. Editing (or renaming/deleting) a migration that has already been applied to any database makes that database refuse to boot with `migration N was previously applied but has been modified` (this is exactly how v0.4.0 broke nc-01: `023_seed_data.sql` was edited after a build had applied it). To change schema or seed data, add a NEW migration with `just migrate-create <name>` - never edit an existing one. CI enforces this: `scripts/check-migration-immutability.nu` (wired into `.forgejo/workflows/check.yml`, DEV-395) fails any PR that modifies/renames/deletes a migration already on `main`, alongside `check-migration-prefixes.nu` (prefix uniqueness, PMS-198).

**A guarded content UPDATE must assert its own row count (PMS-1117).** A migration that rewrites seeded copy (`notification_templates` above all) guards its UPDATE's WHERE clause on the exact text it expects a row to hold, so a tenant who customised that row through the CRUD API keeps their copy and a re-run is a no-op. That contract (migration 096) has one failure mode with no signal at all: when a migration written EARLIER in AUTHORING order lands LATER in NUMBER order (a long-lived branch, most often), an intervening migration can already have rewritten the text the guard expects, and the UPDATE matches zero rows. It commits anyway, `_sqlx_migrations` records it applied, and nothing distinguishes it from one that did its work. This hit the same two rows twice: migration 139 guarded `auth.password_reset` / `auth.welcome` on text migration 116 had already rewritten, so the two highest-volume customer-facing emails shipped unbranded for months, and migration 152 then guarded `auth.welcome` on 139's (never-applied) output and matched zero rows for the same reason one migration downstream. Neither was caught by review, CI, or deploy - only an unrelated test failure, and later a human reading the file next to it. Every guarded content UPDATE written from migration 210 onward must therefore wrap the UPDATE in a `DO $$` block, capture `GET DIAGNOSTICS matched = ROW_COUNT` immediately after it, and call `mokosh_assert_content_rows_matched(matched, expected, context)` (the helper migration 208 adds) so a mismatch RAISEs and fails the migration instead of silently no-opping; migration 209 applies the same helper to `notification_templates`' known-fragile rows as a non-empty-content sanity check. `scripts/check-guarded-content-migrations.nu` (wired into `just check` and `check.yml`) enforces the convention on every migration after prefix 209: a WHERE clause guarding on a free-text column's literal (`subject`, `body_text`, `body_html`, `name`, `description`) with no `GET DIAGNOSTICS` in the same file fails the build. It applies only to migrations written after it, the same limitation every convention-based check in this file carries; 139/152/203/204 are immutable and are not retrofitted.

**A migration that names a role needs that role to exist wherever migrations run (PMS-988).** `db::provision::provision_roles` creates `mokosh_migrator` and `mokosh_app` at server startup, BEFORE `Database::new` and the migrations, so a real deployment can `GRANT ... TO mokosh_app` in a migration and it works. The Postgres-backed suite has no server startup: `#[sqlx::test]` connects to a bare cluster as the superuser, creates a database per test and runs the migrations itself, so nothing satisfies that precondition and a GRANT to an absent role is a hard 42704 that fails every test in the suite before its body runs. That is what migration 207's closing GRANT did. `scripts/test-db-roles.sql` is the one statement that closes the gap, run by `.forgejo/workflows/integration.yml` against the job's postgres service and by `just ensure-test-db-roles` (a dependency of `test-integration` and `verify-demo`) against the dev cluster; it reproduces the role NAME only, because the privileges belong to `src/db/provision.rs` and a second copy of them would drift. A migration granting to some other role means adding it there in the same change - a GRANT that only works where the server booted first is a migration that passes review and fails CI.

**A migration that creates a table grants it to `mokosh_app` in the same file (PMS-1265).** The provisioner reaches the app role only for tables `mokosh_migrator` creates (`ALTER DEFAULT PRIVILEGES FOR ROLE mokosh_migrator`) or that exist at a full provision (an admin-URL boot). A deployment whose migrations run as another owner, which staging's do (`mokosh`), leaves every later table invisible to the app pool: contact create and list went 500 there with `permission denied for table contact_sync_links` because migrations 220-229 created seven tables with no GRANT. Migration 235 re-runs the provisioner's grants over every table; after it, write `GRANT SELECT, INSERT, UPDATE, DELETE ON <table> TO mokosh_app;` beside every `CREATE TABLE` (210 and 218 are the shape). `db::provision::tests::every_new_table_is_granted_to_the_app_role` fails `cargo test --lib` on a migration after 235 that does not.
