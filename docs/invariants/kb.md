# Knowledge base invariants

Scope: KB versions and comments.

Each section below is a convention moved verbatim from the repo `CLAUDE.md` (PMS-1437), which keeps a one-line index entry linking here. A new convention adds its full text here and one index line in [`CLAUDE.md`](../../CLAUDE.md).

## Versions (PMS-1126)

A KB version says who, what kind and why, and the article says who last wrote it (PMS-1126): `kb_article_versions.edited_by_id` has been `NOT NULL` since migration 012, so attribution was never missing, only undisplayed; migration 200 adds `change_note`, `change_kind` (`create` for the snapshot `create_article` seeds inline, `edit`, `restore`, backfilled from `version_number = 1`) and `restored_from_version`, and `kb_articles.updated_by_id`, which every write path stamps (edit, restore, metadata-only edit) and which is NOT backfilled: `ARTICLE_SELECT` in `knowledge_base/service.rs` is the one column list every article read shares and resolves the last editor as the row's `updated_by_id` else the latest version's editor, with names from `users` and "Unknown" for a row that is gone, never an id. A `change_note` on `PUT /kb/articles/{id}` is trimmed onto the version the save creates and dropped when the save creates none, because there is no version for it to explain. `POST .../versions/{n}/restore` takes `RequireManager` like the PUT it is a form of (it carried only the module gate, so a technician could rewrite an article to any past version), takes an optional `{ "change_note" }`, and answers the version it wrote rather than the article. Edit, restore and delete write `audit_log` rows through `article_snapshot`, and `kb_articles` is in `HISTORY_ENTITY_TYPES`. The contact projection carries none of this: a contact does not get staff identities.

## Comments (PMS-1128, PMS-1129, PMS-1130)

KB comments are a staff plane with no customer half (PMS-1128, PMS-1129, PMS-1130): `kb_article_comments` is a NEW table rather than a generalisation of `ticket_notes` (whose ticket FK, email tracking, contact authorship and `note_type` a KB comment must not inherit), one level deep (`parent_id` names a root, enforced in the service), resolvable at the root by any staff role, edited or soft-deleted by the author or an admin (a manager deliberately not, the ticket-note rule), and it has no visibility column on purpose: a contact holding `kb:read` reads articles through the same page staff do, so the one way internal discussion cannot leak onto a customer-visible article is for there to be no customer-visible comment; every comment route sits behind `RequireKnowledgeBase` alone, which a contact bearer never satisfies. An `@handle` is parsed server-side by `knowledge_base::mentions`, a copy of the client's rules (the directory handle, the first name, the full name joined with a dot and with nothing; a token naming two people names nobody), so the chip and the notification point at the same person; `kb_comment_mentions` is the once-only guard (rows written in the comment's transaction, `kb.comment.mention` dispatched after commit once per row THIS write inserted, minus the actor) and its template and rule are seeded, backfilled and copied to new tenants like the other transactional events. A root's `anchor` is a W3C `TextQuoteSelector` over the RENDERED text whose SHAPE `knowledge_base::anchor::validate` checks (422 naming the field) and whose meaning the server never reads: resolving it, and calling one an orphan, is the client's job on render, because it alone holds the rendered text; the value is stored and returned as given (minus what the PMS-924 body sanitizer trims off every string, so `prefix` and `suffix` arrive trimmed and the client compares trimmed context) and `anchor_version` records the article version it was taken from.
