# Contacts and mail invariants

Scope: The company mirror, the contact-sync label filter, the note-edit policy and transactional mail audiences.

Each section below is a convention moved verbatim from the repo `CLAUDE.md` (PMS-1437), which keeps a one-line index entry linking here. A new convention adds its full text here and one index line in [`CLAUDE.md`](../../CLAUDE.md).

## Company mirror (PMS-1069)

A contact's company mirror is written with its link, never alone (PMS-1069): `contacts.company_id` is a mirror of the primary `contact_companies` row (PMS-806) and `recompute_contact_mirrors` re-derives it from that table on every update, so a contact holding the mirror with no link lost its company on the first edit of any field, silently. `contacts::ensure_primary_company_link` is the one write that gives a mirror its link, and the three writers outside `modules/contacts` (email intake's auto-created sender, the tenant portal-admin contact, the dev seeder) call it in the same transaction as their INSERT; migration 198 repairs the rows they already wrote, which is migration 108's backfill applied again, and `update_contact` calls the same function when the request names neither `companies` nor `company_id`, so a row that arrives divergent by any other route heals on the edit instead of losing its company to it. `recompute_contact_mirrors` stays a PURE derivation and is still allowed to null a `company_id` it finds no link for, because that is what an explicit empty `companies` list means and a rule that could never null one would make unlinking impossible; what makes that safe is that the mirror can no longer be written without its link, which is enforced in source rather than remembered by `contacts::service::mirror_writers`, a `cargo test --lib` scan failing any `INSERT INTO contacts` that names `company_id`, `phone`, `mobile` or `fax` without the child write beside it.

## Note editing (PMS-974)

Who may edit a ticket note is a tenant policy, and the edit shows up where a technician looks (PMS-974): `tickets/note_editing` is `off`, `author_or_admin` (the default, which is exactly the PMS-931 gate, so an unset tenant behaves as before) or `author_or_manager`, a closed set `validate_setting_value` refuses anything outside of, read by `TicketService::note_edit_policy` and given meaning by `NoteEditPolicy`. Tenant-level rather than an organization default with an MSP override, because the tenant IS the MSP. It is the WHO gate only: `note_edit_block` (a customer's words, an emailed public note, a time-entry mirror) refuses on the row's state whatever the policy says, and `TicketService::note_editable_by` is the conjunction, which is what `TicketNoteResponse.can_edit` answers on every served note through the one `note_response` constructor in the routes (`false` for a contact session), so a client shows an Edit control only where the PUT would accept. The audit row PMS-931 wrote was reachable only at the table: `list_entity_history` for `tickets` now also returns the `ticket_notes` rows whose snapshot names the ticket, minus their `create` rows (the journal shows those), typed by `EntityHistoryEntry.entity_type` and tied to the note by `entity_id`; migration 205's partial expression index on `new_values ->> 'ticket_id'` is what keeps that arm off a scan. The SPA half (a Tickets setting, the journal reading `can_edit`, rendering a note-edit history entry) is the MAPPS follow-up.

## Mail audiences (PMS-1140)

A transactional mail serves one audience, and a second audience is a second event (PMS-1140): `auth.password_reset` and `auth.welcome` are STAFF mails and keep migration 116's `{{app_name}}` copy (PMS-789); `auth.portal_password_reset` (a customer resetting their portal password, named after the MSP the way `auth.portal_grant` and `auth.login_link` already are; PMS-1343 removed its dispatch site and the row stays seeded because migrations are immutable) and `auth.portal_welcome` (the MSP admin a tenant provisions, the only template carrying `{{client_portal_url}}`) are the portal halves, seeded and backfilled by migration 206 and copied to new tenants by `TenantService::seed_default_config`. The rule is forced by the renderer rather than chosen: `notifications::render_template` is a flat `{{key}}` replacer with no conditionals that emits an unsupplied key VERBATIM into the recipient's inbox, so one template covering two dispatch sites with different context keys ships `{{salutation}},` to a real person - which is exactly what the shared welcome did, because migration 106 gave it `{{salutation}}` and the portal path supplied only `display_name`. Migration 152 tried to bridge the same split with `{% if client_portal_url %}` and would have shipped a literal `{% if %}` had its guard matched, which is why its portal-URL paragraph is now in a template with one dispatch site instead. The rule migration 173 stated first: a dedicated event type, never a conditional. Adding a mail means checking whether its dispatch sites share an audience AND a context contract, and a test asserts on the RENDERED row in `notifications`, never on the template, because a template cannot show you the key nobody supplied.

## Sync labels (PSA-70 E, PMS-1358)

The label selection IS the import filter, and a blank one is not "everything" (PSA-70 E, PMS-1358): `contact_sync::sync::plan` returns `NotSelected` for a record carrying none of the selected labels, on every sync rather than only the first, and `ContactSyncEngine::run` refuses a connection whose selection is empty before it reads the source at all. David's requirement was to import the label that names his clients and nothing else, so the half that is easy to get wrong is what happens LATER: a contact moved out of that label stops being updated, because the MSP no longer agreed to hold its data, and is NOT tombstoned, because the MSP still holds the contact. What makes the second half work is that `seen.insert` runs before the filter, so a record present in a full read counts as seen and the absent-means-deleted pass at the end skips it; moving that insert below the filter would delete every contact that left the label, silently and on a full read only. PMS-1358's own acceptance criteria asked for a blank selection to mean "import everything", and that was declined deliberately: it is the personal-contacts dump the same ticket's Goal rejects, and it is one configuration mistake away from importing an MSP's entire address book. If it is ever wanted, it is an explicit sentinel the admin chooses (the `UNGROUPED_ID` shape), never the default state of a fresh connection.
