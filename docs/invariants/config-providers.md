# Configuration and providers invariants

Scope: The config registry, providers, deployment mode, storage, the email backend, outbound-URL screening, integration status and tenant OAuth clients.

Each section below is a convention moved verbatim from the repo `CLAUDE.md` (PMS-1437), which keeps a one-line index entry linking here. A new convention adds its full text here and one index line in [`CLAUDE.md`](../../CLAUDE.md).

## Storage seam (PMS-910)

Stored files go through one seam (PMS-910): `crate::storage` owns the root and the layout for every kind of stored object, and `StorageConfig::from_env` is the ONLY reader of `STORAGE_ROOT`. Before it, ticket attachments, the tenant logo and KB attachments each read that variable and built their own path, which had already produced two defects: tickets and the logo fell back to `./attachments` while KB fell back to `/data/attachments`, so an unset variable split uploads across two roots in one process; and tenant scoping had three different answers (`{tenant}/{id}`, `{tenant}.{ext}`, and a flat `{id}` with no tenant at all). `ObjectProvider` takes an `ObjectKey` of a tenant plus an object identity and never a path, so a caller cannot assemble one. The layout is pinned by a test in that module, because every file already on a customer's volume is at one of those paths and getting an arm wrong 404s an attachment that is still on disk rather than failing loudly. A ticket attachment is opened from `(tenant_id, id)` rather than from `ticket_attachments.storage_path`, which is still written (the column is `NOT NULL`) and no longer read. Every kind is addressed by its tenant since PMS-960, which moved KB attachments from a flat `kb-articles/{id}` to `{tenant}/kb-articles/{id}`, and every kind sits UNDER its tenant since the follow-up that moved the live logo from `tenant-logos/{tenant}.{ext}` to `{tenant}/logo.{ext}` (the tenant was in that path all along, in the filename; what changed is that one directory per tenant is now the layout without exception, which is what a per-tenant bucket or quota would later be built on, and `{tenant}/branding/` is deliberately not where it went, because that holds the content-addressed frozen copies and the live logo is the opposite of those). The full table is in `docs/architecture.md`. On the KB move: the public read still presents nothing but the v4 id (an `<img>` carries no `Authorization` header, PMS-923), but the storage layer no longer makes that bargain too, so a key built for one tenant cannot name another's object. The path those files came from stays addressable as its own `ObjectKind::LegacyKbAttachment`, because they are still sitting at it on volumes this code cannot reach; a separate variant rather than a fallback inside `LocalProvider`, because a blanket fallback applies to every read and is reachable from any key, which is the hole being closed. Its only two callers derive the tenant from a database row rather than from a request. `KbAttachmentMover`, and `TenantLogoMover` for the logo, walk the files over, registered on the `Scheduler` at an hour: the scheduler fires every job once at startup, so that is one-shot with no maintenance window plus a retry if a rename fails, and it is driven by `files.storage_path` so a completed migration costs one query returning no rows. It moves the file first and updates the ledger second, because a row naming a path before the bytes are there is the one ordering that can lie, and it leaves an attachment whose bytes are at neither path completely alone rather than dressing a missing file up as a migrated one. Every stored object also gets a `files` row through `FileLedger` (PMS-957), keyed on the object's own id and holding `ObjectKey::relative_path` rather than an absolute one, because the root is deployment configuration; that table is what `TenantUsage.storage_bytes` sums, and it had a reader and no writer from the PMS-128 split until then. A logo's row is keyed on its tenant and upserted, since replacing one must not add to the rollup. `files.file_size` is the source of truth for anything spanning features (the tenant rollup, later retention and quotas) while a feature's own `file_size` column answers that feature's API, and the duplication is deliberate for now. Local stays the default, because no integration is a hard requirement.

## Storage provider (PMS-958)

The storage provider is chosen once per process (PMS-958): `storage::shared()` hands every feature an `Arc<dyn ObjectProvider>` built from `STORAGE_PROVIDER` into a `OnceLock`, and `main` calls `storage::init_from_env()` first so a misconfigured provider ends startup rather than the first upload. A process-wide handle rather than a constructor argument, because the provider is constructed at thirteen sites across the router, the tenants routes, billing and the seeders, and an object-store client owns a connection pool that is only useful if shared; `utils::net` and `utils::client_ip` hold their env-derived configuration the same way. Before this, `dyn ObjectProvider` appeared nowhere and six structs held `LocalProvider` by name, so the seam PMS-910 documented was not one. Unset or blank is `local`; a typo is a boot error rather than a fall back, the `SECRET_BACKEND` rule. `s3` is `storage::s3::S3Provider`: no client crate, because the trait needs five requests (PUT, GET, HEAD, DELETE, and PUT with `x-amz-copy-source` for the atomic `rename`) and no listing or XML, so the whole cost is a SigV4 signer that is checked against two published AWS vectors; either SDK crate would add its own HTTP stack to the PMS-781 dependency layer. It is S3-COMPATIBLE, not AWS: `STORAGE_S3_ENDPOINT` is required and path-style is the default, because that is what MinIO, R2 and Backblaze serve. The object key is `ObjectKey::relative_path` joined with `/`, so tenant scoping is the same string on the wire and is tested the same way. The credential is operator env, which IS the PMS-912 rule (a deployment credential lives beside `INFISICAL_CLIENT_SECRET`; only a tenant credential belongs in the `SecretProvider`), and storage is per deployment; a per-tenant bucket later is a `(bucket, credentials)` lookup in front of the same five requests, since the key already carries the tenant. `tests/s3_storage.rs` runs against a real MinIO when `STORAGE_S3_ENDPOINT` is set (CI starts a pinned, checksum-verified binary in the job because a `services:` entry cannot be handed the `server` argument the image needs; `just dev-s3` starts one in the dev stack) and skips loudly otherwise; it sets `STORAGE_PROVIDER=s3` in its own process only. No migration moves objects between providers.

## Config registry (PMS-982)

Configuration has one read path and a declared registry (PMS-982): `src/config/` holds `ConfigProvider` with `EnvProvider` as its default, and `crate::config::get` is how every configuration value is read. Two things make it hold, and the abstraction is neither of them, because Bunyip had a working Infisical client and still read secrets from the database. `src/config/registry.rs` declares every key with its tier (bootstrap, what a provider is made FROM, or application) via a `declare_keys!` macro, so a key and its registry entry come from one declaration and `get` takes a `&'static ConfigKey` rather than a string: an undeclared key does not compile. Each declaration also states the release that added the key and whether boot refuses without it (`since`, `required`, PMS-1442), which is what [`docs/configuration.md`](../configuration.md#all-variables) is rendered from. And `config::guard::every_env_read_goes_through_the_provider` fails `cargo test --lib` on an environment read anywhere in `src/` outside `src/config/` and `ENTRY_POINTS`, which names eight files with one stated reason each (the host-side CLI, the role provisioner, and the providers of record whose selection variable or construction values a provider cannot be built from, `MOKOSH_DEPLOYMENT_MODE` among them because it chooses the providers). It shipped with no allowlist of migrated reads and a test saying so, the `finance_gate::UNGATED` shape. Every declared key resolves at boot into a numbered `Generation` recording the value AND which provider served it; a lazy per-read resolution was rejected because it makes that second answer a moving target. `crate::config::refresh()` rebuilds the generation, carrying bootstrap keys across unchanged, and is what a test that mutates the process environment calls to be seen (`tests/common/mod.rs` does it once in `boot_with_db`). No caller's emptiness, trimming or default rule moved: those are the feature's rules, `get` answers `Some("")` for a blank value, and the reads were relocated without changing one. `scripts/check-env-example.nu` reads the registry as its CODE set, which is what finally made `BrandingAssetStore::max_bytes` visible: it computes its key from a closed match on `(AssetScope, BrandAssetKind)`, so a literal-only scan saw none of its six keys and five of them were in neither `.env.example` nor `compose.dev.yml`.

## Provider naming (PMS-1010)

A selectable implementation is called a provider (PMS-1010): `SecretProvider` with `DatabaseSecretProvider` and `InfisicalSecretProvider` in `src/secrets/`, `ObjectProvider` with `LocalProvider` and `S3Provider` in `src/storage/`, each selected by one `provider_from_env`, beside the `PaymentProvider` and `RmmProvider` that already used the word. One concept had three names before this - the code said store, the architecture said provider, the tracker said backend - and a reader could not tell whether they were three things. The operator-facing variable for secrets is still `SECRET_BACKEND` and the mismatch is deliberate there: renaming it breaks every existing deployment, and `.env.example` plus `scripts/check-env-example.nu` would have to move in lockstep, for a vocabulary change with no operator benefit. Storage was the other half of that sentence until PMS-1317, which renamed it to `STORAGE_PROVIDER` - what changed is not the argument but the method: a DEPRECATED ALIAS makes the rename cost nothing to a deployment that has not moved, so "breaks every existing deployment" stopped being true. The same route is open for `SECRET_BACKEND` whenever it is worth doing. A new seam of this kind is named `<Capability>Provider`, its implementations `<Impl><Capability>Provider` or `<Impl>Provider`, and its selection enum `<Capability>ProviderKind`.

## Deployment mode (PMS-1011)

The deployment mode is the hosting profile (PMS-1011): `MOKOSH_DEPLOYMENT_MODE` keeps its two values and its `self-hosted` default, and additionally supplies a DEFAULT PROVIDER per capability - configuration, secrets, authentication, email, storage - as a data table in `src/utils/deployment.rs` (`SELF_HOSTED_PROVIDER_DEFAULTS`, `SAAS_PROVIDER_DEFAULTS`), so a third mode later is a data addition and no second deployment-shape variable exists. Nothing in the self-hosted column reaches outside the deployment (`EXTERNAL_SERVICE_PROVIDERS` and the test over it), which is what "the customer image boots and serves with no Bunyip, no Infisical and no object store" means concretely. Authentication is the only row where `saas` differs (bunyip ahead of the legacy local path, which stays until PMS-981); the other four match self-hosted because the criterion is to reproduce CURRENT deployed behaviour, and that behaviour is whatever the SaaS deployment's own environment sets - writing `infisical` or `s3` in as a DEFAULT would switch a deployment that sets neither, and `InfisicalSecretProvider::from_env` refuses to build without its variables, so the guess would present as a deployment that no longer boots. The profile locks nothing: an explicit `SECRET_BACKEND` / `STORAGE_PROVIDER` / `SMTP_HOST` / `OIDC_ISSUER` wins for its own kind, and `DeploymentMode::resolve_providers` records per kind whether the profile or the operator decided it, which `main` logs one line per kind at boot (every kind, not only the deviations, because a provider left on by a default has to be visible rather than assumed; PMS-989 reports from that record). The parse behaviour is split by consequence and both halves are deliberate: `parse` / `from_env` keep PMS-902's warn-and-fall-back-to-self-hosted for MAIL DISPATCH, where a typo must not silently stop password-reset mail, while `parse_for_providers` / `from_env_for_providers` refuse an unrecognised value and name the legal ones for PROVIDER SELECTION, where the same typo would silently run on another profile's providers. `docs/dev-docs/self-hosted-vs-saas.md` carries the table and the split. The profile is read in ONE place, `main`, which hands each capability module the NAME it defaults to (`DeploymentMode::default_provider_for`) rather than the mode itself: PMS-904's `only_the_auth_service_and_the_startup_wiring_know_the_deployment_mode` guard exists so a mail gate cannot be placed one level too high, and `secrets` and `storage` care which provider they got, not which deployment shape chose it. A capability module that needs a profile default takes a `&str`, so that guard stays a source scan for the type name and needs no exceptions.

## Email backend

Email backend selection: `MailerConfig::from_env().build()` returns `SmtpMailer` if `SMTP_HOST` is set, `LogMailer` otherwise. `SMTP_USERNAME` without `SMTP_PASSWORD` is a hard error at startup (fail-loud, not silent degrade).

## Outbound URLs (PMS-805, PMS-809)

Outbound-URL screening (PMS-805, PMS-809): every outbound fetch whose URL comes from a request or from tenant-editable configuration runs through `utils::net::guard_outbound_url`, which resolves the host and refuses any address `is_non_public_ip` rejects, before the first connect and again on every redirect hop. Three callers: the company website probe (`modules/contacts/website_probe.rs`, ports pinned to 80/443), the ticket-automation `webhook` action (`modules/tickets/automation.rs`, refusal logged with the rule id and the blocked address), and `TacticalRmmProvider` (`modules/rmm/provider.rs`, refusal is an `AppError::Configuration` surfaced in `rmm_connections.last_error`; redirects are not followed). Do not copy the predicate or the resolve loop: a second definition of either fails `utils::net`'s `exactly_one_definition_in_the_crate` test. `OUTBOUND_PRIVATE_ALLOWLIST` is the operator escape hatch (comma-separated hostnames, IPs, or CIDRs) for a self-hosted integration that really does live on a private network; unset means no exemption. Fetches whose URL comes from operator env are deliberately NOT screened (`INFISICAL_ADDRESS`, the Stripe API base, the `OIDC_ISSUER` JWKS, the fixed upstream version check).

## Payment status (PMS-1312)

Whether a payment provider is connected is `integrations.status`, and one function writes it (PMS-1312): PMS-1310 created `integrations` and deliberately held no row for Stripe or PayPal, because `payment_gateway_configs.is_active` already answered that question and a second answer to one question ends in two rows disagreeing; the registry recorded it as a `ConnectionHome::Elsewhere` entry per provider and the service refused connect, disconnect and a capability change for both. Migration 256 backfills a row per gateway and the entries flip to `ConnectionHome::Integrations`, so both surfaces now work: the payments settings page, where the credential and the per-provider settings are entered, and the integrations page, where a tenant says what it delegates. They cannot disagree because `integrations::connection::set_payment_connection` is the only writer of the status and both call it, and every serving read (the Pay Now decision, which provider mints a checkout session, which tenant a webhook delivery resolves against, the partial-payment floor, and the flag the gateway list serves) goes through the one `CONNECTED_GATEWAY_JOIN` fragment so "connected" has one definition. Three things are easy to get wrong here. A connection home is NOT a credential home: `registry::CredentialHome` says which `SecretKind` addresses a provider's credential, Stripe's stays `PaymentGateway` because its key, webhook secret, test-mode flag and validation pass already live on the payments surface and reproducing them would be a second place to enter one credential, so `connect` there takes no credential, refuses one that is sent, refuses a provider with no gateway row, refuses a row whose credential is in neither place, and `disconnect` leaves the credential alone (the gateway DELETE removes it). `payment_gateway_configs.is_active` is RETIRED but written: it is a one-way mirror kept for exactly one release so a deployment that rolls back to the previous image still serves, since a column dropped out from under that image is every gateway silently off and a webhook resolving nothing after the card was charged, and `billing::service::retired_gateway_flag` fails `cargo test --lib` on any read of it outside the writer. And `authorize_net` gets no row at all: it is in the gateway table's CHECK and in no registry entry, so `set_payment_connection` skips a provider `integrations.provider` refuses, which cannot hide an activation because `upsert_payment_gateway` already refuses to activate anything outside `billing::provider::SUPPORTED`.

## Google client (PMS-1340)

The Google OAuth client is the HOST's, and no tenant holds one (PMS-1430): the pair (`GOOGLE_CONTACTS_CLIENT_ID`, `GOOGLE_CONTACTS_CLIENT_SECRET`) is a `GovernedSecret` served by the declared `AppSecretProvider`, read once at boot by `OauthClient::from_app_secrets`, and handed to the service. This REVERSES PMS-1264 (one client on the system tenant) and PMS-1340 (one per tenant, with the first as a fallback), and the reversal is worth understanding rather than just recording. PMS-1340's reasoning was sound about what a tenant owns: the consent screen a customer reads names an application, the API quota is drawn from one, and so is the verification status. What it did not price is what a tenant-owned client COSTS the tenant, which is a Google Cloud console walkthrough before they can import a single contact: a project, the People API, a consent screen, test users, three scopes, a Web application client, an id and a secret pasted back. Walking it end to end (PMS-1216, evidence on PMS-1428) is what produced PMS-1430, and it produces one of two bad outcomes: an External app left in Testing hands out refresh tokens Google expires after seven days, and one published without verification is capped at 100 users behind an unverified warning. Competing products ship one vendor-owned verified application and the MSP presses Connect. So the client is the deployment's identity now, and a tenant sees `configured` or nothing. Three things follow. Both halves are governed, never an id in configuration beside a governed secret, because they would then resolve from different providers and a mismatched pair fails at Google with an error nobody can place. A half-configured host is a boot error naming the missing key, never a silent fall-through, because there is no next rung to fall to. And a connection made under a retired client cannot be migrated: Google binds a refresh token to the application that issued it, so `invalid_grant` marks the connection `reconnect_required` and the admin is asked to connect again, which migration 258 and `contact_sync::client_cleanup` deliberately do not hide by deleting the connection.

## One-shots (PMS-1320)

A one-time correction is a one-shot, not a job (PMS-1320): work that walks existing objects to where a layout change says they now belong runs ONCE per process start, through `scheduler::one_shot::spawn_once`, and never on an interval. Three of these sat on the `Scheduler` at an hour (`KbAttachmentMover`, `TenantLogoMover`, `GatewayCredentialMover`) for one reason: the scheduler fires every registered job once immediately at startup, so an hourly registration was the cheapest way to get a boot-time run, and the interval came free as a retry. What it cost is a process carrying three recurring jobs whose whole purpose was a correction that completes, which from outside is indistinguishable from maintenance the design depends on, and which has to be re-explained every time somebody asks what runs every hour. The obvious alternative, a migration, is NOT available and it is worth knowing why before reaching for it: a migration runs inside Postgres, and what these move is bytes in `crate::storage` on a volume or in a bucket, or a credential into the secret provider over the network. Only the `files` ledger row is SQL, and rewriting a ledger row without moving the file it names is the one ordering that can lie (PMS-957). An operator command was also declined, because a deployment nobody tells keeps serving off the legacy read fallback forever and the correction never completes; running at boot means every deployment that takes the upgrade completes it. What is given up against the hourly tick is retrying a transient failure an hour later rather than at the next restart, against a `WARN` line naming the pass either way. `scheduler::one_shot::tests::no_mover_is_registered_on_the_scheduler` reads `main.rs` back under `cargo test --lib` and fails a `scheduler.register` line that names a `_mover`, because the pull toward registering one again is exactly how they got there.

## Tenant first (PMS-1318)

Every stored object puts its tenant first, and the exceptions are listed (PMS-1318): tenant isolation has to hold at the STORAGE layer and not only in the database, because a directory shared across tenants is what makes one tenant's file reachable from another's key at all. `storage::tests::every_object_kind_puts_its_tenant_first` asserts the property over every `ObjectKind` rather than over the paths somebody remembered to write down, and `every_object_kind_is_sampled` reads `relative_path`'s own match arms back out of the file so a variant added without a sample fails instead of going untested - which is exactly how `FinancialDocument` sat unpinned through four releases. `NOT_TENANT_SCOPED` names the two `Legacy*` read paths with a reason each and asserts they really are still unscoped, because a legacy arm that quietly gained a prefix would mean its mover is walking files somewhere nothing reads. The one writer of the upload root OUTSIDE that seam is `BrandingAssetStore` (`src/modules/branding/assets.rs`), whose `(Tenant, Logo)` pair goes through `ObjectKey` and whose other five do not: `tenant-favicons/`, `tenant-backgrounds/` and the three `company-*` directories, the last of which carry no tenant at all. That is not a cross-tenant read through the API, because the routes serving them are deliberately public with the id as the credential and no tenant-scoped key is presented; what it costs is the prefix a per-tenant bucket, quota, export or provider migration is built on, which is the stated reason the logo moved. PMS-1397 closes it; until then `branding::assets::tests::the_unscoped_pairs_are_the_ones_pms_1318_found` holds the list against the store's own classifier, so a sixth pair on the local-path layout fails rather than joining them quietly. The operator-facing layout is `docs/configuration.md` under "Storage layout", gaps included, because a documented layout that omits its exceptions is worse than none.

## Storage names (PMS-1317)

Every storage setting is `STORAGE_`-prefixed, and the old names are deprecated aliases (PMS-1317): `STORAGE_PROVIDER`, `STORAGE_ROOT` and the `STORAGE_S3_*` block, read in ONE place, `crate::storage::env`, which resolves each setting's current name and its alias together and is the entry point the config guard names for them. Before it they were `ATTACHMENT_DIR`, `STORAGE_BACKEND` and six bare `S3_*`: three naming schemes for one subsystem, which is why a walk through a deployment's compose file looking for where storage is configured came back with nothing. `ATTACHMENT_DIR` was the worst of them, naming one of the four things kept under that root. The aliases exist because the compose file that sets these lives in ANOTHER repository, so the rename and the compose change cannot land together: a hard rename would mean the first deploy reads no root, falls back to the compiled-in default, and serves 404s for every file already on the volume - a data-loss-shaped outage caused by a vocabulary change. Three rules make the half-migrated state safe and each has a test: the current name wins when both are set (or the new one looks broken mid-migration), a BLANK current name does not shadow a working alias (compose forwards every key with a `:-` empty default, so this is the ordinary case and not the edge one), and using an alias logs one line per NAME rather than per read. `mokosh-server provider-status` lists every storage setting with WHICH NAME supplied it, so "has staging moved yet" has an answer; that row used to name the provider and no keys at all, which is the gap David actually hit. `crate::storage::env::ALL` is the list to delete from one release after every deployment has moved. Branding stopped reading the root a second time in the same change: a second reader would have kept asking for `ATTACHMENT_DIR` while the provider moved to `STORAGE_ROOT`, splitting one process's uploads across two roots, which is the PMS-910 defect reintroduced by the rename meant to prevent it. PMS-1316 is that defect's own issue and what closed it is the pair of guards, not another sweep: `storage::tests::no_module_outside_storage_carries_its_own_root` fails `cargo test --lib` on the default-root literal appearing anywhere outside `src/storage/`, which is the SECOND FALLBACK half, and `config::guard::every_env_read_goes_through_the_provider` already refuses the SECOND READ half. Those are the only two ways a module can acquire a root of its own, and the reason they are enforced rather than remembered is that branding's copy survived PMS-910 untouched and was caught three releases later only because a rename would have stranded it. `only_the_test_harness_picks_a_storage_root` is the same rule for the suites and watches BOTH names, since a guard that knew only the pre-rename one would have waved through the first suite to name `STORAGE_ROOT`.
