# CI, release and repo hygiene invariants

Scope: Branches and PRs, runner labels, the OCI cache, publish tags, single build, workspace deps, `cargo machete`, release image layers, env parity, migration versions, releases, `#[mokosh_test]` and naming.

Each section below is a convention moved verbatim from the repo `CLAUDE.md` (PMS-1437), which keeps a one-line index entry linking here. A new convention adds its full text here and one index line in [`CLAUDE.md`](../../CLAUDE.md).

## Branches

Branches: `fix/...`, `feat/...`, `chore/...`. Forgejo PRs via `fj pr create` (host `dev.a8n.run`). `gh` is not installed.

## Runner labels (PMS-719, GOV-43)

CI runner labels (PMS-719, GOV-43): a job that compiles on the runner requests `RUNS_ON_OPENSUSE_DEV_LATEST` (only that image ships `cc` / `gcc` / `ld` plus glibc and OpenSSL headers); everything else stays on `RUNS_ON_OPENSUSE_BASE_LATEST`. Base plus a compile fails at `linker cc not found` on a cold cache (PMS-705, PMS-706); the fix is the label, never a run-time `zypper install gcc`. `scripts/check-runner-labels.nu` (in `just check` and `check.yml`) enforces this and requires every `runs-on:` to carry a comment justifying its label.

## OCI cache (PMS-720, GOV-20)

OCI build cache (PMS-720, GOV-20): `build-oci-image.yml` builds on a `docker-container` buildx driver and caches to the runner's built-in Actions cache server (`cache_from type=gha`, `cache_to type=gha,mode=max,ignore-error=true`), with `crazy-max/ghaction-github-runtime@v3` re-exporting `ACTIONS_CACHE_URL` / `ACTIONS_RUNTIME_TOKEN` so a raw `docker buildx build` can reach it. The retired `type=inline` and `type=registry` `:buildcache` backends are banned. `scripts/check-oci-build-cache.nu` (in `just check` and `check.yml`) enforces this; because `ignore-error=true` makes a dead cache go green silently, read freshness from the build log's `importing cache manifest from gha` line, not the exit code.

## Publish tags (PMS-733)

Image publish tags (PMS-733): the publish train comes from the trigger, not `git describe`. A `v*` tag push publishes `:vX.Y.Z` only, a `main` push publishes `:latest` only, and a push to a branch on `BRANCH_ALLOW_LIST` in `oci-build/get-tags.nu` publishes that branch's own tag only (the branch name with `/` replaced by `-`), so staging can run a feature branch without `:latest` moving. A branch off that list publishes nothing: it is filtered out by `on.push.branches`, rejected by the job's ref guard, and would fail loud in `get-tags.nu` rather than fall back to `:latest`. To publish from a new branch, add it to the const AND to both places in `build-oci-image.yml`; `scripts/check-oci-publish-tags.nu` (in `just check` and `check.yml`) fails the build if the three disagree.

## Single build (DEV-612)

Single build per commit (DEV-612): a workflow that compiles gates the merge on `pull_request` into main and never repeats that build on `push: main`. A `push: main` run fires after the merge has already landed, so it gates nothing, and on 28 of the last 50 merges the merged tree was byte-identical to the pull-request head, meaning `check.yml` and `integration.yml` recompiled a known answer for a measured 189s + 440s of runner time per merge. What blocks an unbuildable commit is unchanged: the pull-request run of `check.yml` is the gate David added the build for, and on the merge path `build-oci-image.yml` compiles the merge commit itself with `cargo build --release --bins`, so a merged tree that does not compile fails loudly and publishes no `:latest`. What is deliberately given up is post-merge clippy/fmt and the test suites re-run against a merged tree that differs from the head; the zero-cost way to close that is Forgejo branch protection's "require the branch to be up to date", which makes the two trees equal by construction. `e2e.yml` keeps both triggers and is correct: it compiles nothing, and its two runs do different work (a deploy-sync poll after the merge, a reachability check on the pull request). `scripts/check-single-build.nu` (in `just check` and `check.yml`) enforces this and prints the per-workflow classification it decided from.

## Workspace deps (PMS-785)

Workspace dependency table (PMS-785): `[workspace.dependencies]` in the root `Cargo.toml` lists only crates a member actually inherits with `<crate> = { workspace = true }`, because that is the only way an entry reaches the build graph. An entry nobody inherits pins a version and a feature set the build never uses (`tower-http` pinned `["cors", "trace"]` there while the root package independently pinned a six-feature superset), and a member that re-pins a crate the table already covers reopens the same ambiguity. `scripts/check-workspace-deps.nu` (in `just check` and `check.yml`) fails on either shape; `cargo machete` cannot, because it only reads each package's own `[dependencies]` / `[dev-dependencies]` / `[build-dependencies]`. To share a new crate, add the workspace entry and the member's `{ workspace = true }` line in the same change.

## Unused deps (PMS-780)

Unused dependencies (PMS-780): `cargo machete` runs in `just check` and `check.yml` as a blocking gate, so a crate declared in `Cargo.toml` with no call site fails the PR. `pulldown-cmark` and `minijinja` had been compiled on every cold build for nothing. Response compression is brotli-then-gzip: `CompressionLayer::new()` offers only the algorithms whose `tower-http` cargo features are compiled in, so `compression-br` must stay in the feature list (guarded by the negotiation tests in `src/api/router.rs`).

## Image layers (PMS-781)

Release image layers (PMS-781): `oci-build/Dockerfile` compiles third-party dependencies against stub sources in their own layer, then copies the real `migrations/`, `build.rs`, `crates/` and `src/` and compiles the workspace crates in a second layer, so a source-only change reuses the dependency layer instead of recompiling ~330 crates. A layer is the shape the CI `type=gha,mode=max` cache exports; a `--mount=type=cache,target=/build/target` is not, which is why the registry cache mount stays but no `target/` mount was added. The `MOKOSH_GIT_HASH` / `MOKOSH_BUILD_DATE` `ARG`+`ENV` block sits BELOW the dependency layer on purpose: those values change on every build and an `ENV` above the layer would invalidate it every time. Adding a workspace member means adding its `COPY <member>/Cargo.toml`, its stub `src/lib.rs`, and its `--package` to the `cargo clean` that drops the stub artifacts; the clean is what makes the second compile deterministic, because `COPY` preserves the build context's older mtimes and cargo would otherwise call the stubs fresh.

## Env parity (PMS-836)

Environment-variable parity (PMS-836): `compose.dev.yml` declares the dev `server` service's environment as an explicit per-key map with no `env_file:`, so it ENUMERATES the container's environment. A variable the code reads with no line there cannot be set in dev at all: the operator follows `.env.example`, edits `.env`, gets no error, and the feature stays off. That shipped `SPA_BASE_URL`, `ABUSE_CONTACT_EMAIL`, `PUBLIC_API_BASE_URL`, `TENANT_LOGO_MAX_BYTES`, `STORAGE_ROOT`, `IP2LOCATION_DB_PATH`, `IP2PROXY_DB_PATH` and `LOGIN_APPROVAL_ENABLED` unreachable. Adding a configuration read therefore means declaring the key in `src/config/registry.rs` (PMS-982) AND adding a `.env.example` key AND a compose line whose `:-` default reproduces the code's own fallback; `scripts/check-env-example.nu` (in `just check` and `check.yml`) reads the registry as its authoritative CODE set and fails on either omission, on a `.env.example` key nothing consumes, and on a stale allowlist entry. The allowlist in that script carries one stated reason per deliberate asymmetry (build-time vars, the host-side bootstrap CLI's `.env.infisical` vars, `INFISICAL_ADDRESS` versus `MOKOSH_SERVER_INFISICAL_ADDRESS`). A forwarded-but-unset key arrives as `""`, so every reader must treat empty as unset. Uploads (`STORAGE_ROOT`, which holds ticket attachments and the `tenant-logos/` subdirectory) live on the `dev-mokosh-attachments-${USER}` volume at `/data/attachments` so a logo survives a rebuild.

## Migration versions (PMS-965)

Two migrations cannot share a version (PMS-965): `_sqlx_migrations` is keyed on it, so a duplicate makes every database fail to finish migrating and, since migrations run at startup and a failure is fatal, a deployment that pulls that tree does not boot. common's shared `check-migration-versions` recipe (PC-79) runs on every pull request and cannot catch this by itself, because the collision is created BY the merge of two branches that each held only their own number. What prevents it is Forgejo branch protection's "Block merge if pull request is outdated" (`block_on_outdated_branch`) on `main`, enabled under PMS-1056: it forces the second branch to rebase onto the first, at which point the prefix guard sees both files on the pull request where they can still be renumbered. Read the live value with `GET /api/v1/repos/psa-systems/mokosh-server/branch_protections` and the token `fj` stores; `fj repo branch-protection` does not exist in the installed `fj`, whatever older notes say (corrected under PMS-1426). PMS-965 also shipped a `migration-collision.yml` workflow that re-ran the two guards on `push: main`; it only ever alerted after the merge had landed, and it was removed once the setting was on (PMS-1056). If a collision does land, renumber the file that has NEVER been applied, which is the one that loses the sort: the winner's checksum is already recorded on every half-migrated database, so moving the loser lets those databases resume by themselves while moving the winner leaves them needing hand repair. A rename that is provably safe goes into `migration_rename_allowed` in `justfile`, the shared recipe's allow-list (PC-82), one destination path per entry with its reason in a comment beside it; it is empty today because the PMS-965 rename has long been on `main`.

## Integration required (PMS-1426)

`main`'s branch protection requires `Check / * (pull_request)`, `E2E / * (pull_request)` and `Integration / * (pull_request)`. The third was added under PMS-1426; before that a pull request whose Postgres-backed suite was red was still mergeable, and 10 of 39 consecutive merges had landed that way.

Requiring it was not a setting change on its own, and that is the part worth keeping: a required check that fails for reasons unrelated to the change under review blocks every merge in the repository, which is the PMS-1408 lesson. So the job's own failure rate was measured first (10 of 64 pull-request runs between PMS-1398 and PMS-1426) and every one of those failures read, with `just ci-log`. All 10 were two tests whose verdict is a wall clock, neither of them a real assertion failure. Both were fixed where the measurement was wrong (`concurrent_login_health_latency` compares against this machine's own idle baseline instead of a fixed 30ms; `notification_worker_transactions` discriminates at half the relay latency it is measured against); the p99 test still carries `retries = 2` in `.config/nextest.toml`, sound only because a real regression there is deterministic across attempts; the notification-worker test's retry and widened threshold were removed by PMS-1436, which scoped the probe to the worker's own `application_name` and eliminated the cross-backend noise outright rather than tolerating it.

Read the live required set with `GET /api/v1/repos/psa-systems/mokosh-server/branch_protections`, the same call as `block_on_outdated_branch` above. A fourth workflow does not join that list without the same evidence: the failure rate, the cause of every failure in the window, and a fix for anything that was not the code under review.

## Releases

Releases: `just create-release <major|minor|hotfix>` bumps `Cargo.toml`, pushes a `release/v<X.Y.Z>` branch, opens the PR. CI tags + publishes on merge.

## Test databases (PMS-1254)

A database-backed test is `#[mokosh_test]`, and the migrations run once (PMS-1254): `#[sqlx::test]` created a database per test and applied every migration into it, so a suite of about 1,300 cases paid the 243-migration run 1,300 times to produce one identical schema. `crates/mokosh-test` migrates ONE template database, named after a digest of the migration set compiled into the test binary, and each test's database is a `CREATE DATABASE ... TEMPLATE` clone of it; `crates/mokosh-test-macros` holds the attribute, split out only because a proc-macro crate can export nothing else, and `mokosh-test` re-exports it so a test binary names one dependency. Four properties are what make it safe to trust. The template is named after its contents, so editing or adding a migration builds a different template instead of reusing a schema that no longer matches the tree - a suite silently running against last week's schema would be worse than a slow one. That property held only on paper until PMS-1398, and the way it broke is worth keeping: the NAME came from a runtime walk of `migrations/` while the CONTENTS came from `sqlx::migrate!`, which embeds at COMPILE time and, on stable, registers nothing as a build dependency (`proc_macro::tracked_path` is nightly-only). A run whose binary predated a new migration therefore computed the name of the new set and filled the template with the old one, and since `ensure_template` decides whether to build from whether that NAME exists, the mismatch was permanent and no later rebuild repaired it; `drop_stale_templates`, which keeps the current name and drops the others, kept precisely the poisoned one. On a clean tree that presented as migration 252's six `integrations` cases plus `rbac_route_coverage` failing for no reason a diff could explain. The name now comes from the EMBEDDED set (`template_digest` over each `Migration`'s version, description and checksum), so name and contents have one source: a stale binary computes the OLD name and correctly reuses the old template, and a rebuilt one computes a new name and builds. `crates/mokosh-test/build.rs` is the other half, emitting `cargo:rerun-if-changed=../../migrations` so the crate actually recompiles when a migration lands (the root `build.rs` does the same for `src/db/pool.rs`), and `the_embedded_migration_set_matches_the_migrations_directory` is the tripwire that fails loudly if it ever stops working, because a binary carrying a set that is not the tree's is the silent half of this defect. It is built under a `_building` name and renamed only once every migration has applied, so a process killed part-way leaves a carcass the next run drops rather than a template that looks finished. The build runs under a session-level advisory lock, so with nextest's process-per-test the first arrival builds and the rest wait, and the one line naming the template is printed by the building process alone, which is what shows the migrations ran once. And the attribute is deliberately a near-copy of what `#[sqlx::test]` expanded to - the same current-thread runtime, the same pool closed with the same ten-second timeout and the same message, the database dropped on success and KEPT on a panic with its name printed - because the ~1,300 bodies are unchanged and any difference there would be a difference in what they mean. A test that wants a database takes `#[mokosh_test]` and one `pool: PgPool` argument; there is no argument form, because `#[sqlx::test(migrations = "./migrations")]` and the bare form were never different tests.

## Client repo (PMS-856)

Client repository name (PMS-856): the SPA repository is `mokosh-apps`, and the name it replaced resolves to nothing. `repo_hygiene::the_former_client_repo_name_stays_gone` in `src/lib.rs` scans the working tree under `cargo test --lib` (a `check.yml` step) and fails if the old name reappears anywhere, so no new script, recipe or CI step carries the ban.

## Docker naming

Docker resource naming: every service/volume/network is prefixed with the app name; dev resources get an extra `dev-` prefix. Sub-service data stores sort adjacent to their parent (`dev-backup-infisical-postgres`, not `dev-backup-postgres-infisical`).
