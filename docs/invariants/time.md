# Time and work days invariants

Scope: Time entries, timesheets, work days and segments, "today", and tenant-day jobs.

Each section below is a convention moved verbatim from the repo `CLAUDE.md` (PMS-1437), which keeps a one-line index entry linking here. A new convention adds its full text here and one index line in [`CLAUDE.md`](../../CLAUDE.md).

## Entry kind (PMS-942)

Employee time versus client work (PMS-942): `time_entries.entry_kind` is `client` or `employee`, and it is the axis every rule that differs between a customer's work and the MSP's own time keys on. One table, not two, because PMS-943 needs a day's timesheet to break down ticket work, project work and administrative time - the employee's day and the client's work are two axes over the same fact. A named column rather than `company_id IS NULL`, because PMS-413 (migration 062) already gives every tenant an `internal` company and MAPPS-243 attributes a General entry to it, so an inferred axis would make every one of those rows wrong. `company_id` is nullable and only `client` entries are required to name one; `employee` entries carry no ticket, project, task or contract (enforced by CHECK) and are never billable (enforced in the service, because `is_billable` DEFAULTs TRUE and a constraint would have aborted migration 119's backfill on pre-existing overhead rows). A query that means "work a client pays for" filters on `entry_kind = 'client'`, never on which company id the caller passed: the internal company is a real `companies` row, so before this the MSP's own overhead time was invoiceable by naming it.

## Timesheets gate (PMS-943)

Timesheets are a gated module (PMS-943): `timesheets` is a `module_config` row like the nine `gated_module!` entries beside it, and the five timesheet routes carry `RequireTimesheets` on top of `RequireTimeTracking`. Two modules, not one, because logging time and submitting a week of it for approval are different features: a one-person MSP still logs and still bills. `RequireModuleEnabled` answers 404 rather than 403, so a disabled feature is indistinguishable from a route that does not exist - which is also why "not mounted" is not the implementation: the router is built once per process and serves every tenant, so a per-tenant decision cannot be a mount-time one. The flag's STARTING value comes from `tenants.kind` (`personal` off, `org` on), and the first invitation, which promotes a personal tenant to an org, turns it on; after that it is the operator's setting and nothing re-derives it.

## Work day (PMS-950)

A day is derived from its segments (PMS-950): `work_day_segments` holds one `work` or `break` segment per row with a start, an end (NULL while open) and the `date` it belongs to, and there is no day row, because a day row would be a second home for facts the segments already hold and the only one able to disagree with them. Clocking in opens a `work` segment; clocking out closes whichever segment is open; a break closes the open `work` segment and opens a `break` one at the same instant in one transaction, and ending it reopens `work`, so lunch is "a clock-out" without a second concept. The partial unique index on the open segment per user is the double-clock-in guard, the shape `active_timers.UNIQUE(user_id)` has for the item timer: a 409 from the pre-check, and the index closes the race. The clock writes no `time_entries`; `GET /workday` reads the day's entries by what they are attached to (per ticket, per project, Administrative for `entry_kind = 'employee'`, Unattached for client work naming neither, which PMS-942 says is the client's time) and reports the signed gap between clocked and logged rather than resolving it. The break routes read the PMS-943 `timesheets/track_breaks` setting and answer 404 with it off, the way the module gate does; every route carries `RequireTimeTracking` AND `RequireTimesheets`. A segment keeps its `date` across midnight, and the date is the client's (the way `time_entries.date` is) or today in the user's own zone via `mokosh_types::datetime::user_today` on `users.timezone`, the preference the dashboard's "today" already follows (PMS-253); never the UTC day, which puts an evening clock-in in the Americas on tomorrow. The migration is numbered 188 rather than 135 because `mokosh-contact-login` holds 135 through 187, all applied on staging, and PMS-965 renumbers the file that was never applied.

## Today (PMS-1027)

"Today" is where the person is, never the UTC clock (PMS-1027): `users.timezone` has existed since migration 003 and `mokosh_types::datetime::user_today(now, &user.timezone)` is the one way to ask what day it is for a user, the way the dashboard has since PMS-253. Every route that defaults a date threads the caller's zone into the service (invoice date, credit-note issue date, task due date, the report windows), a stopped timer is dated by its OWNER's zone because the entry is theirs, and a quote's read-time expiry takes the READER's day through `CallerContext::today`, which answers for a staff user (`users.timezone`) and a contact (`contacts.timezone`) alike. A new `Utc::now().date_naive()` in serving code is the defect this closed; the only ones left are the tenant-level jobs (recurring invoicing, contract expiry, the block-hours period), which have no user and are PMS-1030. The test shape that pins it is two users 26 hours apart (`Pacific/Kiritimati`, `Etc/GMT+12`), so at any instant one of them is on a different calendar day from UTC.

## Tenant day (PMS-1030)

A tenant-level job takes the tenant's day (PMS-1030): the recurring invoice generator and the contract expiry sweep have no user to ask what day it is, so `settings::read_tenant_zone` answers with the default `business_hours` row's `timezone` (else `UTC`) and `user_local_date(now, &zone)` is the day. Not a new `tenants.timezone` column, because the SLA's business hours already hold the zone this MSP's day happens in and a second home is how the two come to disagree; the SLA clock itself keeps reading the row its POLICY names, because a policy's hours are the policy's. The expiry sweep is cross-tenant, so its candidate scan uses the latest date any zone can be on (UTC's day plus one, no zone being further east than +14) and each tenant is then drained against its own today. Before this the worker's hourly run dated a Vancouver MSP's 1st-of-month invoice on the last day of the previous month and expired an Auckland contract at noon the day after it ended. `consume_hours` was never a site: `consume_for_entry` hands it midnight of `time_entries.date`, so the day is the entry's own.

## Segment edits (PMS-1145)

A recorded work-day segment can be corrected, and who may is the tenant's answer (PMS-1145): `PUT` and `DELETE /workday/segments/{id}` carry the same two module gates as the five clock routes, and `timesheets/segment_editing` (`SegmentEditPolicy`: `off`, `owner_or_admin` the default, `owner_or_manager`) decides who. The `tickets/note_editing` shape from PMS-974 deliberately, because it is the same question with the same failure mode: a value outside the closed set read as the default in silence, which `validate_setting_value` refuses at the write. Before this the five routes all acted on *now* and a segment, once written, could not be changed by anything - a gap against `time_entries`, the row a customer is actually billed from, which has been editable throughout. Three things are decided rather than mechanical. The row is edited IN PLACE and the change goes to `audit_log` (`entity_type = 'work_day_segments'`, both sides in `old_values`/`new_values`), because that is where this codebase's history lives and a void-and-replace column would be a second home for it that every existing query - the partial unique index on the open segment included - would have to learn to skip. An explicit `null` on `ended_at` REOPENS a segment (the double option is what tells "leave the end alone" from "undo the clock-out") and is refused with a 409 when the person already has another open, because the index would refuse it anyway and a constraint name is not an explanation. And NO day is frozen: `work_day_segments` is read by `src/modules/time_tracking/work_day.rs` and nothing else, an invoice bills `time_entries` and a timesheet approves `time_entries`, so a correction changes neither and there is nothing for a freeze to protect - if that stops being true, the module doc there is what has to change with it. A forgotten clock-out is the adjacent problem (PMS-1146) and the correction is what recovers from it: `clock_in` still refuses while any segment is open whatever its date, which is right (a day that was never clocked out is still that day), but the refusal now NAMES that day and how long the segment has run and points at the correction, because "Already clocked in; clock out first" on a Tuesday morning reads as an instruction to clock out of Monday and records the night as worked. `WorkDayResponse.date_source` says the same thing on the read side: `GET /workday` with no date answers with the OPEN segment's day rather than today, which a client cannot detect by comparing dates because it does not know whether the server chose the day or was handed it. No auto-close and no cap: an auto-close invents an end time nobody chose, and with `PUT /workday/segments/{id}` able to close a segment at a chosen time there is a recovery that does not.
