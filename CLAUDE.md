# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mokosh Server: PSA (Professional Services Automation) REST API for MSPs. Rust + Axum + SQLx + PostgreSQL. Two binaries:

- `mokosh-server`: long-running HTTP API (`src/main.rs`).
- `mokosh-bootstrap`: one-shot CLI for first-run Infisical setup and OIDC client registration (`src/bin/mokosh-bootstrap.rs`).

## Common commands

All driven through `just` (see `justfile`). Required tooling: `just`, Nushell `0.112.2`, Docker + Compose v2, Rust `1.94.1` (the exact patch `rust-toolchain.toml` pins, so rustfmt and clippy match CI), `sqlx-cli` for migrations, `cargo-machete` for the unused-dependency gate (`cargo install --locked cargo-machete`).

### Dev stack

A single Traefik-routed dev stack (PMS-511 folded the former SSO overlay into `compose.dev.yml`):

```
just dev                   # Traefik-routed stack at https://${USER}-mokosh-api.a8n.run (mokosh-server + Postgres + mailpit)
just dev-infisical         # opt-in: Infisical + its Postgres (compose profile: infisical)
just dev-s3                # opt-in: MinIO, and fills the blank S3_* keys in .env (compose profile: s3)
just down                  # stop the dev stack, remove orphans (volumes preserved)
just dev-clean             # stop + wipe volumes + remove .env (keeps .env.infisical)
just infisical-bootstrap   # one-time after `just dev-infisical`, fills INFISICAL_* in .env
```

OIDC client registration recipes (`register-client`, etc.) were removed with mokosh-auth in PMS-295: bunyip is the sole OP and owns its own client registry, so RPs register with bunyip, not mokosh.

`just dev` rewrites `MOKOSH_HOST_BIND_IP` and `USER` in `.env` each run (`USER` names the per-developer containers, volumes, networks and the `${USER}-mokosh-api.a8n.run` route; the LAN IP, discovered from `sys net | where name =~ 'eth0|br0'`, is recorded but no longer consumed by `compose.dev.yml`, since PMS-496 moved the `postgres`/`mailpit` host publishes to loopback and the `server` is ingress-only via Traefik). First run generates `.env` from the committed `.env.example` (via the `ensure-env` recipe, a dependency of `just dev`), minting fresh random values for every self-owned secret (PMS-490: DB passwords, `JWT_SECRET`, `ENCRYPTION_KEY`, the Infisical secrets) and leaving third-party credentials as empty placeholders. It does not copy a file; an existing `.env` is left untouched, so the generation runs once per clone.

`just dev-infisical` rewrites `MOKOSH_SERVER_INFISICAL_ADDRESS` in `.env` to `http://infisical:8080`, which compose passes to the `server` container as `INFISICAL_ADDRESS` (restart `server` to pick it up). It stays empty on a plain `just dev` so the readiness probe reports `checks.infisical == "skipped"` rather than 503ing against the profile-gated service (PMS-707). The separate plain `INFISICAL_URL` in `.env` is a different key: the host-side `http://localhost:28002` that the bootstrap CLI reads when `just infisical-bootstrap` runs it. PMS-853 renamed that template key onto the name the CLI actually reads; the previous name was read by nothing.

`just dev` requires the shared external `network-traefik-public` to already exist. (Before PMS-295 it also needed a local Ed25519 keypair for mokosh-auth's OP signing; that subsystem is gone, so no key material is provisioned now. The bunyip-as-OP Resource-Server path verifies tokens against bunyip's JWKS over the network.)

### Auth: two independent mechanisms (PMS-295)

bunyip-as-OP is the only OP. PMS-295 removed mokosh-auth (mechanism 2, mokosh's own OIDC OP) entirely; the server now accepts two independent auth paths in parallel, and failing to mount one does NOT disable the other:

1. **Bunyip-as-OP Resource-Server** (`src/modules/auth/oidc_rs.rs`): mokosh verifies bunyip-issued `at+jwt` Bearer tokens against bunyip's JWKS. Configured by `OIDC_ISSUER` + `OIDC_AUDIENCE`. This is the path the mokosh-apps SPA and the E2E suite actually use; tokens come from `api.<tld>` = bunyip. Mokosh holds no signing key and exposes no `/oauth2/*` endpoints.
2. **Legacy HS256 cookie auth** (`src/modules/auth/`): JWT in cookie, Argon2 password hashing, session rows in `user_sessions`. Used by the original PSA endpoints. `AuthMiddleware` decodes the cookie into an `AuthState`. Routes opt in via `RequireAuth` / `RequireRole` / `RequireAdmin` / `RequireManager` / `RequireFinance` extractors. TOTP (RFC 6238) + MFA recovery codes for this path live in `src/utils/totp.rs` + `src/utils/recovery.rs` (relocated from the removed `mokosh-auth-crypto` crate in PMS-295).

Both paths run the same principal gate (PMS-698): `AuthService::ensure_principal_usable` rejects a `users.status != 'active'` row and a tenant whose `status != 'active'`, so deactivating a user or suspending a tenant takes effect on the very next request regardless of which mechanism minted the token. The PMS-681 `iat`-vs-`password_changed_at` cutoff stays legacy-only on purpose: bunyip owns the credential on path 1, so a mokosh-side password change is not a revocation signal there. So does the MAPPS-531 session check, for the same reason: every legacy access token names a `user_sessions` row in its `sid`, and `ensure_user_and_tenant_active` refuses the request once that row is gone, so a sign-out revokes the access token and not just the refresh. That is why sign-out is a DELETE here where the portal (below) needs a stamp, and why `POST /api/v1/auth/logout-all` (PMS-880, audit F3) needs no cutoff column of its own: deleting every row for the user fails the same check for every token they hold.

**History (PMS-291 / PMS-292 / PMS-289)**: mokosh-auth was a configured-but-unused second IdP (`crates/mokosh-auth*`). PMS-289 made a misconfigured mokosh-auth a fatal boot error, which took staging+prod down (PMS-292 restored service by provisioning keys - interim path B). PMS-295 is the path-A follow-up: tear mokosh-auth out so `MOKOSH_AUTH_*` env, the `crates/mokosh-auth*` workspace members, and the `mokosh-server-secrets` volume all go away. The server boots fine with no `MOKOSH_AUTH_*` env present.

PMS-837 removed the last auth-adjacent workspace crate: `google-oauth-flow` and the `/api/v1/auth/google` + `/api/v1/auth/google/callback` popup routes it served went away with the `GOOGLE_OAUTH_*` and `OAUTH_SUPER_ADMIN_EMAILS` env vars. No client ever called them (three parity audits between 2026-07-30 and 2026-08-14 found the routes unconsumed, and mokosh-apps still has no reference). `google_oauth_routes_stay_unmounted` in `src/modules/auth/routes.rs` is the guard that fails if either mount returns; the `user_oauth_identities` table stays, because migrations are immutable.

### Portal credentials are a third, fully separate plane (PMS-820)

A portal identity is a `contacts` row (`portal_password_hash`, `is_portal_user`); a platform identity is a `users` row. One email address can legitimately hold one platform account and a portal identity in several tenants at once, so the portal owns its whole credential lifecycle: `POST /api/v1/portal/auth/{login,setup-password,forgot-password,reset-password}` resolve the identity from `contacts` inside the tenant named by `tenant_slug` and never read or write `users`. `/api/v1/auth/forgot-password` is the platform path and resolves against `users` only; an address that is portal-only finds no user there and gets the same silent 200 as any unknown address. Do NOT point the portal at the platform reset endpoints: one credential path serving two identity kinds is the PMS-820 defect, where a customer resetting their portal password reset a staff login instead.

Portal reset tokens reuse the PMS-136 `portal_setup_tokens` row and its `{contact_id}.{secret}` shape (Argon2-hashed, single use, 24h), so redeeming a self-service reset link and redeeming an agent-minted setup link share one replay contract: 204, then 410 on replay, 400 on expired/unknown. Both new endpoints are rate limited by `AuthRateLimiter` (10/min per IP, 3/min per account) exactly as PMS-680 did for the platform path; forgot-password keys the account bucket on `(tenant_slug, email)` because `contacts.email` is only unique within a tenant, and reset-password keys it on the contact id in the token. The mail is queued through the existing `auth.password_reset` template (already copied to every new tenant by `TenantService::create`), so no new template is seeded.

Portal sessions are stateless, so revocation is a cutoff, not a delete (MAPPS-532). `PortalAuthService::login` mints an 8-hour HS256 JWT and writes no session row; `PortalJwtClaims` carries no session id, so there is no portal analogue of `user_sessions` for `POST /portal/auth/logout` to delete. It stamps `contacts.portal_tokens_valid_from` instead, and `portal_auth_middleware` rejects any token whose `iat` predates that stamp - the `users.password_changed_at` shape from PMS-681. Two consequences to keep in mind: a portal sign-out ends that contact's sessions on EVERY device, and the check is strictly `<` so a contact who signs straight back in inside the same second keeps the token they just received. The middleware pays nothing extra for it (the contacts row was already being read for the names PII minimisation keeps out of the JWT), but that read is now the revocation check, so a failure to read it is a 401 rather than the empty-names degrade it used to be.

The portal has no role table; the one role it has is the billing contact (PMS-993). It is `companies.default_billing_contact_id` for the company in the token's `cid` claim, so it is per-company and single-valued by construction, and reassigning it demotes the previous holder in the same write. `contact_snapshot` carries it back as a correlated `EXISTS` in the same read as the names and the cutoff, NOT as a join: that read is the revocation check and a missing row degrades instead of rejecting, so a query that can lose the `contacts` row would turn sign-out-everywhere into a no-op. It is deliberately kept out of `PortalJwtClaims`, so revoking the role takes effect on the next request rather than the next login. `contacts.contact_type = 'billing'` is a classification label and grants nothing; do not overload it, and do not confuse either with `RequireBilling`, which is the agent-side module-enable gate.

### Providers (PMS-1009)

`docs/providers.md` is the contract for every selectable-implementation seam: the provider kinds, the three tiers (bootstrap / application / tenant, separated by bootstrap order rather than by sensitivity), where each is configured, priority, the four boot classifications, refresh, and the migrate-verify-purge workflow. Read it before adding a seam or a second implementation of one, because the parts that are easy to get wrong (a silent fallback to the default, a purge that deletes a value not verified elsewhere, an unreachable provider reported as absent) are exactly the parts it fixes. `src/secrets/` and `src/storage/` are the two seams that already follow it; configuration, application secrets, authentication and email do not yet, and `docs/ROADMAP.md` carries the sequencing with each phase linked to its issue.

Two rules from that document bind any change here. Provider enablement is bootstrap configuration, never served by a provider, because configuration that locates configuration cannot live inside what it locates. And a key read outside its provider is the defect the model exists to prevent: Bunyip had a working Infisical client and still served secrets from the database, because nothing forced the read through the seam.

### Routing model

`create_api_router` (`src/api/router.rs`) builds these top-level nests, plus a fallback. Each one states what authenticates a request to it; keep this list in step with the `.nest(...)` calls at the end of `create_api_router`.

- `/api/v1/*` PSA router. Every module exposes either `<name>_routes(service)` (nested under a prefix) or merges directly when it owns multiple top-level prefixes (e.g. `time_tracking_routes`, `projects_routes`, `calendar_routes`, `contracts_routes`, `billing_routes`, etc. all use `.merge`). Authenticated by the session: `auth_middleware` runs globally and populates `AuthState`; route handlers opt in via `RequireAuth` / `RequireRole` / `RequireAdmin` / `RequireManager` / `RequireFinance`.
- `/api/v1/public/*` UNAUTHENTICATED, by design. Nothing authenticates a request to this subtree: no session, no cookie, no bearer, no signature. Everything it serves is listed here. `GET` and `POST /api/v1/public/request-forms/{token}` (`src/modules/forms/public_routes.rs`), where the single-use magic-link token in the URL is the only identity and resolves its own tenant, throttled per client IP by `RequestFormLimiter`. `GET /api/v1/public/tenants/{tenant_id}/logo` (`src/modules/tenants/routes.rs`), which a recipient's mail client fetches straight out of a request-form email and can never authenticate; a tenant with no logo 404s identically to a tenant id that does not exist, and SVG is excluded from the allowed upload types. All three image routes here share one allowlist, `utils::inline_image::check_inline_image_mime`, guarded by a single-definition test the way `utils::net` guards `is_non_public_ip`: they make the same bargain, so they must refuse the same types (PMS-941). `GET /api/v1/public/kb/attachments/{attachment_id}` (`src/modules/knowledge_base/attachments.rs`), an image embedded in a KB article, where the attachment's v4 UUID is the only credential: a browser fetches it as `<img src>`, an `<img>` carries no `Authorization` header, and the SPA holds a bearer rather than a cookie, so there is no authenticated form of this request to make. The cost is real and deliberate: anyone holding the URL can fetch the image even for an `internal` or `client_specific` article. An unknown id and a deleted attachment 404 identically so it is not an existence oracle, SVG is excluded for the same reason as the logo, and the read runs on the migrator pool with a SAFETY note because it has no tenant context to set (PMS-923). `GET /api/v1/public/tickets/attachments/{attachment_id}` (`src/modules/tickets/attachments.rs`), an image embedded in a ticket description or note, for the same `<img>` reason and with one extra guard (PMS-941): `ticket_attachments` has no MIME allowlist and already holds portal uploads and PMS-450 inbound-email attachments, all stored under an authenticated-only contract, so the read serves ONLY rows carrying `is_inline` and that flag is set by nothing but `AttachmentService::create_inline` (image-only via `utils::inline_image`, `note_id` NULL, capped at 5 MiB). A real-but-unflagged attachment 404s exactly as an unknown id does, because the flag is in the WHERE clause rather than a check after the fetch. A handler added here answers anyone on the internet: it needs its own throttle and must expose nothing that a tenant id or a leaked token alone should not unlock.
- `/api/v1/portal/*` portal router with its OWN auth middleware (identity = `contacts` row, not `users`). Authenticated by a portal-tagged Bearer JWT that `portal_auth_middleware` decodes; handlers opt in via `RequirePortalAuth`, or via `RequirePortalBillingContact` (PMS-993) where the handler also needs the billing role: that extractor delegates the 401 to `RequirePortalAuth` and adds a 403 when the contact is not the billing contact of the company its session is scoped to. The three invoice handlers (`/portal/invoices`, `/portal/invoices/{id}`, `/portal/invoices/{id}/pay`) are the only ones behind it today; the role gate runs BEFORE the company-scope check, so a contact without the role gets the same 403 for every id and the cross-company 404 posture is untouched. The `/portal/auth/{login,setup-password,forgot-password,reset-password}` credential endpoints are reachable without either (they are rate limited by `AuthRateLimiter` instead). `POST /portal/auth/logout` is the exception among the `/auth/*` siblings: it needs the bearer it revokes, so it sits behind `RequirePortalAuth`. Never sees `AuthState`.
- `/api/v1/bunyip/*` bunyip webhook receiver (`POST /webhooks/account-deleted`). Authenticated by the `X-Webhook-Signature` HMAC-SHA256 over the body, keyed by `BUNYIP_WEBHOOK_SECRET` (PMS-591), not by a session.
- `/api/v1/stripe/*` Stripe webhook receiver (`POST /webhooks/{tenant_id}`). Authenticated by the `Stripe-Signature` HMAC over the raw body, keyed by that tenant's stored webhook signing secret (PMS-711), not by a session. The tenant id in the path selects which secret to verify against; it is not itself a credential.
- `/api/v1/paypal/*` PayPal webhook receiver (`POST /webhooks/{tenant_id}`), the same `provider_webhook_handler` as Stripe's mounted with `provider_id: "paypal"` (PMS-969). Authenticated by the five `PAYPAL-TRANSMISSION-*` headers, which the provider does not check locally: PayPal signs RSA-SHA256 against a certificate served at a URL in those headers, so the supported path is `POST /v1/notifications/verify-webhook-signature`, sending the headers and body back to PayPal for a SUCCESS or FAILURE. That call is why the prefix is in `RAW_BODY_PATHS` despite not being an HMAC: a byte the sanitizer rewrote is a FAILURE there. The receiver refuses a delivery whose resolved provider is not the one the route names, so a late Stripe delivery to a tenant now on PayPal is a 401 rather than a mis-verified body. PayPal also does not charge on approval; `CHECKOUT.ORDER.APPROVED` is `PaymentEvent::RequiresCapture`, the receiver calls `PaymentProvider::capture`, and the resulting `PAYMENT.CAPTURE.COMPLETED` records the payment.
- Fallback for non-API paths: small HTML "not a frontend" page linking back to the SaaS shell. No authentication; it renders the same page for anyone.

`#[cfg(feature = "multi-tenant")]` gates the `/tenants` CRUD routes; default features are `["multi-tenant", "server"]`. The `server` feature gates HTTP-only code so the library crate can be reused without Axum.

Every JSON request body to every one of those trees passes through `utils::text::sanitize_json_body` (PMS-924) before any extractor sees it: it strips the `Cf` format characters and U+00AD, folds non-ASCII whitespace to a plain space, and trims, at every depth including object keys. A handler therefore never sees `Acme\u{200B}`, and no route can forget to opt in the way a `SanitizedJson<T>` extractor on 156 `Json<T>` handlers would. Two carve-outs, both enforced in that module and both tested. **Secrets** are exempt by field name (`SECRET_FIELD_NAMES`): a password, token, API key or webhook secret is compared byte for byte against something stored elsewhere, so rewriting one is a failed login with nothing in the log. **Signature-verified receivers** are exempt by path (`RAW_BODY_PATHS`: the Bunyip, Stripe and PayPal webhooks, `POST /api/v1/rmm/alerts`), because each verifies the raw bytes (three by HMAC, PayPal by sending them back) and a one-byte rewrite is a 401. Adding a fifth verify-over-body route means adding its `RAW_BODY_PATHS` prefix in the same change. Non-JSON bodies (multipart uploads, attachments) are forwarded byte-identical and never buffered.

### Multi-tenancy

No middleware-level tenant scoping: every service method takes the scope explicitly. Since PMS-139 that scope is a `TenantId` newtype (`src/modules/auth/tenant.rs`) whose in-crate constructor is `pub(crate)` and is reached only through `CurrentUser::tenant()`, so a handler that forgets to thread the caller's tenant no longer compiles instead of leaking across tenants. The deliberate escape hatch is `TenantId::from_trusted`, for the paths where the scope genuinely is not a `CurrentUser` claim: the Stripe and RMM webhook receivers, super-admin `tenants` handlers addressing a path tenant, portal contact sessions, the seeders, and the cross-tenant workers (`calendar/worker.rs`, `sla/worker.rs`, the billing sweep). Cross-cutting issue #8 in `docs/dev-docs/codebase-state.md` records the rollout.

### Migrations

Per-feature files under `migrations/` (split from the original `001_initial_schema.sql` monolith in PMS-128). Embedded at compile time via `sqlx::migrate!`; `migrations/` must exist in the build context (both Dockerfiles copy it). On server start with `RUN_MIGRATIONS=true` (default) migrations run automatically.

**Migrations are immutable once committed.** sqlx stores a SHA-384 checksum of each migration in `_sqlx_migrations` when it applies it, and re-verifies on every startup. Editing (or renaming/deleting) a migration that has already been applied to any database makes that database refuse to boot with `migration N was previously applied but has been modified` (this is exactly how v0.4.0 broke nc-01: `023_seed_data.sql` was edited after a build had applied it). To change schema or seed data, add a NEW migration with `just migrate-create <name>` - never edit an existing one. CI enforces this: `scripts/check-migration-immutability.nu` (wired into `.forgejo/workflows/check.yml`, DEV-395) fails any PR that modifies/renames/deletes a migration already on `main`, alongside `check-migration-prefixes.nu` (prefix uniqueness, PMS-198).

### Module status

Most route groups have real handlers. `src/api/router.rs` nests/merges ~30 implemented modules (`auth`, `contacts`, `tenants`, `tickets`, `billing`, `projects`, `calendar`, `contracts`, `quotes`, `assets`, `rmm`, `sla`, `saved_reports`, `workflows`, `time_tracking`, and more); the old `stub_routes()` 501 placeholder mechanism is gone. The report-export route (`src/modules/reports/routes.rs`) serves `csv` and `pdf` (PMS-876) and rejects every other `format` with 400 and not 501: `format` is an enumerated query parameter, so a value outside the implemented set is an out-of-range request rather than a server-side gap (PMS-854). The schema is still ahead of the handler layer in places. `docs/dev-docs/codebase-state.md` is a frozen 2026-05-06 snapshot (PMS-849), not a current per-module status: read it for the `F1..F14` fix ids, the numbered cross-cutting issues that source comments cite, and the shallow-DTO traps in tickets, and read `src/api/router.rs` plus the "Routing model" section above for what is actually mounted. Do not append to it; a new route group is recorded in the "Routing model" list.

## Conventions specific to this repo

- Branches: `fix/...`, `feat/...`, `chore/...`. Forgejo PRs via `fj pr create` (host `dev.a8n.run`). `gh` is not installed.
- CI runner labels (PMS-719, GOV-43): a job that compiles on the runner requests `RUNS_ON_OPENSUSE_DEV_LATEST` (only that image ships `cc` / `gcc` / `ld` plus glibc and OpenSSL headers); everything else stays on `RUNS_ON_OPENSUSE_BASE_LATEST`. Base plus a compile fails at `linker cc not found` on a cold cache (PMS-705, PMS-706); the fix is the label, never a run-time `zypper install gcc`. `scripts/check-runner-labels.nu` (in `just check` and `check.yml`) enforces this and requires every `runs-on:` to carry a comment justifying its label.
- OCI build cache (PMS-720, GOV-20): `build-oci-image.yml` builds on a `docker-container` buildx driver and caches to the runner's built-in Actions cache server (`cache_from type=gha`, `cache_to type=gha,mode=max,ignore-error=true`), with `crazy-max/ghaction-github-runtime@v3` re-exporting `ACTIONS_CACHE_URL` / `ACTIONS_RUNTIME_TOKEN` so a raw `docker buildx build` can reach it. The retired `type=inline` and `type=registry` `:buildcache` backends are banned. `scripts/check-oci-build-cache.nu` (in `just check` and `check.yml`) enforces this; because `ignore-error=true` makes a dead cache go green silently, read freshness from the build log's `importing cache manifest from gha` line, not the exit code.
- Image publish tags (PMS-733): the publish train comes from the trigger, not `git describe`. A `v*` tag push publishes `:vX.Y.Z` only, a `main` push publishes `:latest` only, and a push to a branch on `BRANCH_ALLOW_LIST` in `oci-build/get-tags.nu` publishes that branch's own tag only (the branch name with `/` replaced by `-`), so staging can run a feature branch without `:latest` moving. A branch off that list publishes nothing: it is filtered out by `on.push.branches`, rejected by the job's ref guard, and would fail loud in `get-tags.nu` rather than fall back to `:latest`. To publish from a new branch, add it to the const AND to both places in `build-oci-image.yml`; `scripts/check-oci-publish-tags.nu` (in `just check` and `check.yml`) fails the build if the three disagree.
- Single build per commit (DEV-612): a workflow that compiles gates the merge on `pull_request` into main and never repeats that build on `push: main`. A `push: main` run fires after the merge has already landed, so it gates nothing, and on 28 of the last 50 merges the merged tree was byte-identical to the pull-request head, meaning `check.yml` and `integration.yml` recompiled a known answer for a measured 189s + 440s of runner time per merge. What blocks an unbuildable commit is unchanged: the pull-request run of `check.yml` is the gate David added the build for, and on the merge path `build-oci-image.yml` compiles the merge commit itself with `cargo build --release --bins`, so a merged tree that does not compile fails loudly and publishes no `:latest`. What is deliberately given up is post-merge clippy/fmt and the test suites re-run against a merged tree that differs from the head; the zero-cost way to close that is Forgejo branch protection's "require the branch to be up to date", which makes the two trees equal by construction. `e2e.yml` keeps both triggers and is correct: it compiles nothing, and its two runs do different work (a deploy-sync poll after the merge, a reachability check on the pull request). `scripts/check-single-build.nu` (in `just check` and `check.yml`) enforces this and prints the per-workflow classification it decided from.
- Workspace dependency table (PMS-785): `[workspace.dependencies]` in the root `Cargo.toml` lists only crates a member actually inherits with `<crate> = { workspace = true }`, because that is the only way an entry reaches the build graph. An entry nobody inherits pins a version and a feature set the build never uses (`tower-http` pinned `["cors", "trace"]` there while the root package independently pinned a six-feature superset), and a member that re-pins a crate the table already covers reopens the same ambiguity. `scripts/check-workspace-deps.nu` (in `just check` and `check.yml`) fails on either shape; `cargo machete` cannot, because it only reads each package's own `[dependencies]` / `[dev-dependencies]` / `[build-dependencies]`. To share a new crate, add the workspace entry and the member's `{ workspace = true }` line in the same change.
- Unused dependencies (PMS-780): `cargo machete` runs in `just check` and `check.yml` as a blocking gate, so a crate declared in `Cargo.toml` with no call site fails the PR. `pulldown-cmark` and `minijinja` had been compiled on every cold build for nothing. Response compression is brotli-then-gzip: `CompressionLayer::new()` offers only the algorithms whose `tower-http` cargo features are compiled in, so `compression-br` must stay in the feature list (guarded by the negotiation tests in `src/api/router.rs`).
- Release image layers (PMS-781): `oci-build/Dockerfile` compiles third-party dependencies against stub sources in their own layer, then copies the real `migrations/`, `build.rs`, `crates/` and `src/` and compiles the workspace crates in a second layer, so a source-only change reuses the dependency layer instead of recompiling ~330 crates. A layer is the shape the CI `type=gha,mode=max` cache exports; a `--mount=type=cache,target=/build/target` is not, which is why the registry cache mount stays but no `target/` mount was added. The `MOKOSH_GIT_HASH` / `MOKOSH_BUILD_DATE` `ARG`+`ENV` block sits BELOW the dependency layer on purpose: those values change on every build and an `ENV` above the layer would invalidate it every time. Adding a workspace member means adding its `COPY <member>/Cargo.toml`, its stub `src/lib.rs`, and its `--package` to the `cargo clean` that drops the stub artifacts; the clean is what makes the second compile deterministic, because `COPY` preserves the build context's older mtimes and cargo would otherwise call the stubs fresh.
- Environment-variable parity (PMS-836): `compose.dev.yml` declares the dev `server` service's environment as an explicit per-key map with no `env_file:`, so it ENUMERATES the container's environment. A variable the code reads with no line there cannot be set in dev at all: the operator follows `.env.example`, edits `.env`, gets no error, and the feature stays off. That shipped `SPA_BASE_URL`, `ABUSE_CONTACT_EMAIL`, `PUBLIC_API_BASE_URL`, `TENANT_LOGO_MAX_BYTES`, `ATTACHMENT_DIR`, `IP2LOCATION_DB_PATH`, `IP2PROXY_DB_PATH` and `LOGIN_APPROVAL_ENABLED` unreachable. Adding an `env::var` read therefore means adding a `.env.example` key AND a compose line whose `:-` default reproduces the code's own fallback; `scripts/check-env-example.nu` (in `just check` and `check.yml`) fails on either omission, on a `.env.example` key nothing consumes, and on a stale allowlist entry. The allowlist in that script carries one stated reason per deliberate asymmetry (build-time vars, the host-side bootstrap CLI's `.env.infisical` vars, `INFISICAL_ADDRESS` versus `MOKOSH_SERVER_INFISICAL_ADDRESS`). A forwarded-but-unset key arrives as `""`, so every reader must treat empty as unset. Uploads (`ATTACHMENT_DIR`, which holds ticket attachments and the `tenant-logos/` subdirectory) live on the `dev-mokosh-attachments-${USER}` volume at `/data/attachments` so a logo survives a rebuild.
- Employee time versus client work (PMS-942): `time_entries.entry_kind` is `client` or `employee`, and it is the axis every rule that differs between a customer's work and the MSP's own time keys on. One table, not two, because PMS-943 needs a day's timesheet to break down ticket work, project work and administrative time - the employee's day and the client's work are two axes over the same fact. A named column rather than `company_id IS NULL`, because PMS-413 (migration 062) already gives every tenant an `internal` company and MAPPS-243 attributes a General entry to it, so an inferred axis would make every one of those rows wrong. `company_id` is nullable and only `client` entries are required to name one; `employee` entries carry no ticket, project, task or contract (enforced by CHECK) and are never billable (enforced in the service, because `is_billable` DEFAULTs TRUE and a constraint would have aborted migration 119's backfill on pre-existing overhead rows). A query that means "work a client pays for" filters on `entry_kind = 'client'`, never on which company id the caller passed: the internal company is a real `companies` row, so before this the MSP's own overhead time was invoiceable by naming it.
- Timesheets are a gated module (PMS-943): `timesheets` is a `module_config` row like the nine `gated_module!` entries beside it, and the five timesheet routes carry `RequireTimesheets` on top of `RequireTimeTracking`. Two modules, not one, because logging time and submitting a week of it for approval are different features: a one-person MSP still logs and still bills. `RequireModuleEnabled` answers 404 rather than 403, so a disabled feature is indistinguishable from a route that does not exist - which is also why "not mounted" is not the implementation: the router is built once per process and serves every tenant, so a per-tenant decision cannot be a mount-time one. The flag's STARTING value comes from `tenants.kind` (`personal` off, `org` on), and the first invitation, which promotes a personal tenant to an org, turns it on; after that it is the operator's setting and nothing re-derives it.
- Billable time is armed at creation, not at approval (PMS-944): a `time_entries` row gets `billing_status = 'ready_to_bill'` from `resolve_billing_status` when it is created, and `create_invoice_from_time_entries` bills only that status, so a billable client hour is invoiceable because it was logged. PMS-144 had `approve_timesheet` write that status and it was the ONLY statement that ever did, which made countersigning a week the sole route to an invoice and left a tenant with timesheets off (PMS-943) unable to bill at all. `MileageTrackingService::create` never had the gate and is the shape both now share. Three consequences worth knowing before touching this area. An update must re-resolve the status, or an entry marked non-billable keeps the arming it was created with and is invoiced anyway; passing the current status in is what stops an already-`billed` row being re-armed onto a second invoice. Project and task `actual_hours` / `actual_amount` count `approval_status <> 'rejected'` rather than `= 'approved'`, because nothing on a timesheets-off tenant ever reaches `approved` and every project there would read zero. And approval of a unit of work now lives only where timesheets do: the `/time-entries/{id}/approvals` routes carry `RequireTimesheets`, while `change_request` and `quote` approvals are untouched because they approve a decision rather than a unit of work, and `ticket` approvals never gated anything (`tickets` has no approval column and `ApprovalsService::decide` writes only its own table). Block-hours consumption moved off approval entirely in PMS-951 (see the storage-adjacent bullet below), for the same two reasons: nothing on a timesheets-off tenant reaches approval, and an entry is real when it is logged.
- An invoice's balance is derived in one place (PMS-953): `BillingService::recompute_invoice_balance` owns `amount_paid`, `amount_credited`, `balance_due`, `status` and `paid_at`, computing all five from SQL sums over `payments`, `payment_refunds` and issued `credit_notes` rather than from Rust-side arithmetic. Every write that moves money calls it while holding the invoice row lock from `lock_invoice_totals`, in that order, so a credit racing a payment queues instead of losing one of the two writes (PMS-695). Adding a second updater for any of those five columns is the mistake this guards against: two writers with two rules for one balance is how the halves come to disagree. An issued invoice is immutable and the only correction is a credit note, which is what finally gave `void` a writer; before PMS-953 that status and `written_off` were values the model knew and no code path could reach, because PMS-38 and PMS-39 both deferred the correcting half and only the freezing half shipped. A credit note is issued or voided and never edited, for the reason its invoice is not: the customer holds a copy of both. A statement (PMS-954, `GET /statements`) is a read model over those same rows and writes nothing: it reads only DATED columns (`invoice_date`, `payment_date`, `issue_date`, a refund's `created_at`), never `balance_due` or `amount_paid`, because those are current values and a statement for a period that closed last month has to show what was outstanding then. Its opening balance is computed from everything before the period rather than stored as a running total, for the same reason the balance has one writer: a running total is a third home for a number that already has one, and the only one that can be silently wrong.

- Sending an invoice emails the invoice, and `sent` means it went (PMS-991, PMS-992): on the first transition to `sent`, `update_invoice` resolves the recipient BEFORE the transition (the invoice's billing contact, else the company's `default_billing_contact_id`, either with an address; no guessing beyond that, because PMS-993 settles the recipient as a contact holding the billing role and rejects picking "some contact"), refuses the send with a 409 naming the company and what is missing when none resolves, and otherwise freezes the invoice, stores the document (PMS-959), and emails it INSIDE the transaction through `email_invoice`, with the document attached (`Mailer::send_with_attachments`) and the portal pay link added only when a gateway is connected. A relay that refuses the message rolls the transition back, so the invoice stays a draft rather than a `sent` nobody received; a send that goes records `emailed_to` and `emailed_at`. `skip_email: true` on the update is the explicit path for an invoice delivered by hand: it freezes and records nobody as emailed, which is what the seeders and the suites that send without a contact say. Because storage is not transactional, a rolled-back send can leave a stale render at the document's key, which is why `GET /invoices/{id}/pdf` reads the store only for a frozen invoice and renders a draft live. Before PMS-991 the mail was gated on the gateway and a fresh install mailed nobody; the "no email rule matches this action" the standup reported was the client's preview modal (MAPPS-642). `SharedMailer` on the test app (`app.mailer.swap`) is how a suite asserts on what the API sent, or refuses it.
- Net terms are a number on the term (PMS-990): `payment_terms.net_days` is what "Net 30" means, and `BillingService::resolve_due_date` is the one rule for a due date the caller did not give: the invoice date plus the net days of the named term, or of the tenant's active default term when none is named, with the term that supplied the count recorded on the invoice; a term with no count (an "On approval" is legitimate) or a tenant with no default falls back to thirty days, the value the time-entry and recurring paths hardcoded before, so nothing moves for a tenant that configured nothing. A given due date is stored as given. Changing an invoice's term without a due date re-derives it, because a Net 15 invoice keeping a Net 30 date carries a term its own dates contradict; changing nothing leaves it alone. The invoice document prints no status line: the bytes are stored at the first send and served unchanged, so a status would read `sent` forever, and a draft preview that printed `draft` would differ from the stored document by that one word. `a_draft_preview_is_byte_identical_to_the_document_stored_at_send` in `tests/issued_documents.rs` pins that preview and send agree, which is what "preview before send" is here: a live render of a draft (`GET /invoices/{id}/pdf`) plus the store at send, not a stored draft render.
- Product catalog and pricing (PMS-955): `products` is a tenant-scoped price list, and `invoice_lines.product_id` / `contract_items.product_id` are optional references to it. The price is NEVER read through the reference. A line stores `unit_price` at the moment it is written and the recurring worker copies `contract_items.unit_price` onto the line it generates, so editing the catalog cannot re-price a signed contract or a document already issued, which matters because an issued invoice is immutable (PMS-953). A product reference is validated against the caller's tenant on write (`assert_product_sellable`), for the same reason `payment_term_id` is (PMS-333): an FK check bypasses RLS, so a foreign-tenant id would satisfy the constraint and link silently. A sold product cannot be deleted (a plain FK reference refuses it, surfaced as a 409) and is retired with `is_active = false` instead; `ProductResponse.in_use` (PMS-1002) says up front whether anything names it, computed as an `EXISTS` on each FK column in the one `PRODUCT_COLUMNS` list every product read and `RETURNING` shares, so a client can withhold Delete where it would be refused. It is advisory and the FK stays the guard. Products price things; `rate_cards` prices labour by work type and by the hour: two axes, not two homes for one thing. Whether a contract item bills is `contract_items.billing_rule` (PMS-956), not `item_type`: `every_period`, `once` or `manual`, because `item_type` says what the item IS and the two were one field, which is how a `product` item came to bill never. The generator selects on the rule, and a `once` item is claimed with `UPDATE ... WHERE billed_at IS NULL` inside the generating transaction, because `contract_invoice_runs` is keyed on `(tenant_id, contract_id, period_start)` and so records that a PERIOD was billed: without the per-item claim a setup fee added in March bills again in April. Omitting the rule on write derives it from `item_type` (`BillingRule::derive`), reproducing today's behaviour for the two types that already billed. The column default is `manual` and the migration backfilled only `recurring_service` and `retainer`, both for one reason: a row nobody was charging for must not start charging, since a missing charge is recoverable where a wrong one is a conversation. `contract_items.billing_frequency` is still read by nothing and was deliberately not overloaded, because its name promises per-item cadence that nothing implements.

- A prepaid block is drawn down when time is logged (PMS-951): `time_entries.contract_id` is derived from the company at create and stop-timer, and `consume_for_entry` draws the hours immediately. It was never set by anything before, so `consume_approved_hours` had read a column no write path wrote since PMS-405 and a block-hours contract was never consumed at all: an MSP billed hourly for work a client had prepaid. Approval is NOT a consumption point and must not become one again, because PMS-943 gates it behind the timesheets module (a tenant with it off would draw nothing) and PMS-944 already made an entry real at creation (so both would draw). `time_entries.hours_consumed` is the APPLIED hours, never the duration, because ten hours against an eight-hour allotment applies eight and leaves two as overage and only the applied part left the balance; `hours_balance_id` names the period row it left, so an entry whose date moves gives back to the period that gave. Both together are the idempotency guard: every claim is `WHERE hours_consumed IS NULL`. An edit releases and re-draws rather than adjusting by a delta, which covers a duration change, a flip to non-billable and a date crossing a period boundary without a case for each. Only billable `client` work draws. A release reads the old values from a `FOR UPDATE` sub-select and not from `RETURNING`, which in Postgres yields the row after the update and would hand back the NULL it just wrote.

- "Today" is where the person is, never the UTC clock (PMS-1027): `users.timezone` has existed since migration 003 and `mokosh_types::datetime::user_today(now, &user.timezone)` is the one way to ask what day it is for a user, the way the dashboard has since PMS-253. Every route that defaults a date threads the caller's zone into the service (invoice date, credit-note issue date, task due date, the report windows), a stopped timer is dated by its OWNER's zone because the entry is theirs, and a quote's read-time expiry takes the READER's day through `CallerContext::today`, which answers for a staff user (`users.timezone`) and a contact (`contacts.timezone`) alike. A new `Utc::now().date_naive()` in serving code is the defect this closed; the only ones left are the tenant-level jobs (recurring invoicing, contract expiry, the block-hours period), which have no user and are PMS-1030. The test shape that pins it is two users 26 hours apart (`Pacific/Kiritimati`, `Etc/GMT+12`), so at any instant one of them is on a different calendar day from UTC.
- An invoice is issued in the tenant's currency (PMS-1028): `settings::read_default_currency` reads `billing_prefs/currency` on the caller's tenant-GUC connection, unset means `USD`, and every invoice writer (`create_invoice`, `create_invoice_from_time_entries`, the recurring generator) resolves the request's currency else the setting; a credit note inherits its invoice's. `invoices.currency` is the per-row home, so an invoice keeps the currency it was issued in when the setting changes. The two `"USD"` literals left in `billing::service` are read-side fallbacks for rows older than the column and say so.

- Stored files go through one seam (PMS-910): `crate::storage` owns the root and the layout for every kind of stored object, and `StorageConfig::from_env` is the ONLY reader of `ATTACHMENT_DIR`. Before it, ticket attachments, the tenant logo and KB attachments each read that variable and built their own path, which had already produced two defects: tickets and the logo fell back to `./attachments` while KB fell back to `/data/attachments`, so an unset variable split uploads across two roots in one process; and tenant scoping had three different answers (`{tenant}/{id}`, `{tenant}.{ext}`, and a flat `{id}` with no tenant at all). `ObjectProvider` takes an `ObjectKey` of a tenant plus an object identity and never a path, so a caller cannot assemble one. The layout is pinned by a test in that module, because every file already on a customer's volume is at one of those paths and getting an arm wrong 404s an attachment that is still on disk rather than failing loudly. A ticket attachment is opened from `(tenant_id, id)` rather than from `ticket_attachments.storage_path`, which is still written (the column is `NOT NULL`) and no longer read. Every kind is addressed by its tenant since PMS-960, which moved KB attachments from a flat `kb-articles/{id}` to `{tenant}/kb-articles/{id}`: the public read still presents nothing but the v4 id (an `<img>` carries no `Authorization` header, PMS-923), but the storage layer no longer makes that bargain too, so a key built for one tenant cannot name another's object. The path those files came from stays addressable as its own `ObjectKind::LegacyKbAttachment`, because they are still sitting at it on volumes this code cannot reach; a separate variant rather than a fallback inside `LocalProvider`, because a blanket fallback applies to every read and is reachable from any key, which is the hole being closed. Its only two callers derive the tenant from a database row rather than from a request. `KbAttachmentMover` walks the files over, registered on the `Scheduler` at an hour: the scheduler fires every job once at startup, so that is one-shot with no maintenance window plus a retry if a rename fails, and it is driven by `files.storage_path` so a completed migration costs one query returning no rows. It moves the file first and updates the ledger second, because a row naming a path before the bytes are there is the one ordering that can lie, and it leaves an attachment whose bytes are at neither path completely alone rather than dressing a missing file up as a migrated one. Every stored object also gets a `files` row through `FileLedger` (PMS-957), keyed on the object's own id and holding `ObjectKey::relative_path` rather than an absolute one, because the root is deployment configuration; that table is what `TenantUsage.storage_bytes` sums, and it had a reader and no writer from the PMS-128 split until then. A logo's row is keyed on its tenant and upserted, since replacing one must not add to the rollup. `files.file_size` is the source of truth for anything spanning features (the tenant rollup, later retention and quotas) while a feature's own `file_size` column answers that feature's API, and the duplication is deliberate for now. Local stays the default, because no integration is a hard requirement.
- The storage provider is chosen once per process (PMS-958): `storage::shared()` hands every feature an `Arc<dyn ObjectProvider>` built from `STORAGE_BACKEND` into a `OnceLock`, and `main` calls `storage::init_from_env()` first so a misconfigured provider ends startup rather than the first upload. A process-wide handle rather than a constructor argument, because the provider is constructed at thirteen sites across the router, the tenants routes, billing and the seeders, and an object-store client owns a connection pool that is only useful if shared; `utils::net` and `utils::client_ip` hold their env-derived configuration the same way. Before this, `dyn ObjectProvider` appeared nowhere and six structs held `LocalProvider` by name, so the seam PMS-910 documented was not one. Unset or blank is `local`; a typo is a boot error rather than a fall back, the `SECRET_BACKEND` rule. `s3` is `storage::s3::S3Provider`: no client crate, because the trait needs five requests (PUT, GET, HEAD, DELETE, and PUT with `x-amz-copy-source` for the atomic `rename`) and no listing or XML, so the whole cost is a SigV4 signer that is checked against two published AWS vectors; either SDK crate would add its own HTTP stack to the PMS-781 dependency layer. It is S3-COMPATIBLE, not AWS: `S3_ENDPOINT` is required and path-style is the default, because that is what MinIO, R2 and Backblaze serve. The object key is `ObjectKey::relative_path` joined with `/`, so tenant scoping is the same string on the wire and is tested the same way. The credential is operator env, which IS the PMS-912 rule (a deployment credential lives beside `INFISICAL_CLIENT_SECRET`; only a tenant credential belongs in the `SecretProvider`), and storage is per deployment; a per-tenant bucket later is a `(bucket, credentials)` lookup in front of the same five requests, since the key already carries the tenant. `tests/s3_storage.rs` runs against a real MinIO when `S3_ENDPOINT` is set (CI starts a pinned, checksum-verified binary in the job because a `services:` entry cannot be handed the `server` argument the image needs; `just dev-s3` starts one in the dev stack) and skips loudly otherwise; it sets `STORAGE_BACKEND=s3` in its own process only. No migration moves objects between providers.
- A selectable implementation is called a provider (PMS-1010): `SecretProvider` with `DatabaseSecretProvider` and `InfisicalSecretProvider` in `src/secrets/`, `ObjectProvider` with `LocalProvider` and `S3Provider` in `src/storage/`, each selected by one `provider_from_env`, beside the `PaymentProvider` and `RmmProvider` that already used the word. One concept had three names before this - the code said store, the architecture said provider, the tracker said backend - and a reader could not tell whether they were three things. The two operator-facing variables are still `SECRET_BACKEND` and `STORAGE_BACKEND` and the mismatch is deliberate: renaming them breaks every existing deployment, and `.env.example` plus `scripts/check-env-example.nu` would have to move in lockstep, for a vocabulary change with no operator benefit. A new seam of this kind is named `<Capability>Provider`, its implementations `<Impl><Capability>Provider` or `<Impl>Provider`, and its selection enum `<Capability>ProviderKind`.

- The deployment mode is the hosting profile (PMS-1011): `MOKOSH_DEPLOYMENT_MODE` keeps its two values and its `self-hosted` default, and additionally supplies a DEFAULT PROVIDER per capability - configuration, secrets, authentication, email, storage - as a data table in `src/utils/deployment.rs` (`SELF_HOSTED_PROVIDER_DEFAULTS`, `SAAS_PROVIDER_DEFAULTS`), so a third mode later is a data addition and no second deployment-shape variable exists. Nothing in the self-hosted column reaches outside the deployment (`EXTERNAL_SERVICE_PROVIDERS` and the test over it), which is what "the customer image boots and serves with no Bunyip, no Infisical and no object store" means concretely. Authentication is the only row where `saas` differs (bunyip ahead of the legacy local path, which stays until PMS-981); the other four match self-hosted because the criterion is to reproduce CURRENT deployed behaviour, and that behaviour is whatever the SaaS deployment's own environment sets - writing `infisical` or `s3` in as a DEFAULT would switch a deployment that sets neither, and `InfisicalSecretProvider::from_env` refuses to build without its variables, so the guess would present as a deployment that no longer boots. The profile locks nothing: an explicit `SECRET_BACKEND` / `STORAGE_BACKEND` / `SMTP_HOST` / `OIDC_ISSUER` wins for its own kind, and `DeploymentMode::resolve_providers` records per kind whether the profile or the operator decided it, which `main` logs one line per kind at boot (every kind, not only the deviations, because a provider left on by a default has to be visible rather than assumed; PMS-989 reports from that record). The parse behaviour is split by consequence and both halves are deliberate: `parse` / `from_env` keep PMS-902's warn-and-fall-back-to-self-hosted for MAIL DISPATCH, where a typo must not silently stop password-reset mail, while `parse_for_providers` / `from_env_for_providers` refuse an unrecognised value and name the legal ones for PROVIDER SELECTION, where the same typo would silently run on another profile's providers. `docs/dev-docs/self-hosted-vs-saas.md` carries the table and the split. The profile is read in ONE place, `main`, which hands each capability module the NAME it defaults to (`DeploymentMode::default_provider_for`) rather than the mode itself: PMS-904's `only_the_auth_service_and_the_startup_wiring_know_the_deployment_mode` guard exists so a mail gate cannot be placed one level too high, and `secrets` and `storage` care which provider they got, not which deployment shape chose it. A capability module that needs a profile default takes a `&str`, so that guard stays a source scan for the type name and needs no exceptions.

- An invoice carries the MSP's identity, frozen (PMS-911): `tenants.branding` gains `legal_name`, `tax_id` and `postal_address`, and `invoices.issuer_snapshot` holds the whole resolved identity as it stood at the FIRST transition to `sent`, written in that same transaction. Not "at issue time": an invoice has no `issued` status, `is_frozen` starts at `sent`, and `issued` belongs to credit notes. Not in the post-commit `just_sent` hook beside it either, which is best-effort so a Pay Now mail failure cannot undo a status change; an invoice must never freeze carrying no identity. The snapshot holds the logo's BYTES, not its URL, because the live logo is written to one key per tenant and overwritten on replace, so a stored reference would re-render every sent invoice with whatever mark is current: `issuer::freeze` copies them to a content-addressed `ObjectKind::BrandingLogo` and keeps the digest, one object per distinct logo rather than one per invoice. `issuer::resolve` composes the whole identity including its fallbacks (`legal_name`, then `company_name`, then the tenant name), so everything downstream reads a resolved value and a future per-company resolver would replace one function. The column is deliberately not backfilled: asserting that invoices already sent carried today's name and address is the exact lie the column exists to prevent, so an absent snapshot falls back to live branding the way those documents always rendered. `GET /invoices/{id}/pdf` renders from the snapshot; `GET /statements/pdf` renders from CURRENT branding, because PMS-954 made a statement a read model that stores nothing and there is no row for a snapshot to hang off - the artefact that was SENT becomes a stored PDF under PMS-959. Both carry `RequireFinance` on top of `RequireBilling`; six older read routes in that file do not, which is PMS-962. `crate::pdf` renders deterministically because PMS-911's byte-identical rule needs it to: printpdf's random trailer `/ID` is rewritten from a digest of the file and an image's `XObjectId` is derived from a digest of the image, since a random one lands inside a compressed content stream that cannot be patched afterwards; PMS-1007 added the third such id, the embedded font's `FontId`, which is a fixed name for the same reason.
- A financial read carries two gates (PMS-962): every handler in `src/modules/billing/routes.rs` takes `RequireBilling` (the per-tenant module gate, 404 when billing is off) AND `_finance: RequireFinance` (the role gate, `super_admin | admin | finance`). Six read routes carried only the first, so a technician refused `GET /invoices` was served `GET /statements`, which holds the same invoice totals plus the whole payment history: the shape of defect PMS-350 exists to have closed. It was not one slip but the same one three times (PMS-953's credit-note reads, PMS-954's statement, PMS-955's product reads), so the rule is enforced in source rather than remembered: `billing::routes::finance_gate::every_billing_handler_also_takes_the_finance_gate` reads the file's own text under `cargo test --lib` and fails on a handler taking one gate without the other, with an `UNGATED` exception list that is empty and has its own test saying so. Adding a read route to that file means adding both extractors, or naming it in `UNGATED` with the reason every role may read it. `rbac_route_coverage.rs` is the behavioural half: the source guard proves the extractor is present, the matrix proves it does what it is there for.
- Two migrations cannot share a version (PMS-965): `_sqlx_migrations` is keyed on it, so a duplicate makes every database fail to finish migrating and, since migrations run at startup and a failure is fatal, a deployment that pulls that tree does not boot. `check-migration-prefixes.nu` runs on every pull request and cannot catch this, because the collision is created BY the merge of two branches that each held only their own number; DEV-612 removed the `push: main` trigger that would have seen it. `migration-collision.yml` runs the two migration guards on `push: main` (it compiles nothing, so `check-single-build.nu` leaves it alone) but it ALERTS rather than gates - the merge has already landed. What gates is Forgejo branch protection's "require the branch to be up to date before merging", which forces the second branch to rebase onto the first. If a collision does land, renumber the file that has NEVER been applied, which is the one that loses the sort: the winner's checksum is already recorded on every half-migrated database, so moving the loser lets those databases resume by themselves while moving the winner leaves them needing hand repair. `check-migration-immutability.nu` carries a narrow rename allow-list for exactly this, one entry per rename with its reason, named by the DESTINATION path because that is how `git diff --name-only` reports a rename.
- The document that was issued is kept, not reproduced (PMS-959): an invoice's PDF is rendered and stored at `ObjectKind::FinancialDocument` inside the transaction that first moves it to `sent`, a credit note's inside the transaction that creates it (it is issued the instant it exists, PMS-953), and `GET /invoices/{id}/pdf` and `GET /credit-notes/{id}/pdf` serve those bytes when there are any. The reason is narrower than it looks and worth keeping straight: branding is frozen (PMS-911) and `pdf::render` is a pure function of its input, so a re-render agrees with what was sent - until somebody edits `billing::documents` or `crate::pdf`, at which point every past document quietly reprints differently. These bytes are insurance against THIS CODEBASE changing, not against the data changing. In the transaction and not after it, because storing afterwards lets an invoice reach `sent` with no document; not before the row lock, because a concurrent edit could make the document disagree with what commits; and the ledger row goes through the same transaction (`FileLedger::record_in_tx`) so a rollback takes both. That required `load_invoice` / `load_credit_note`, transaction-scoped loaders that `get_invoice` / `get_credit_note` wrap, so there is one assembly of what a document contains rather than two. A live render is the fallback for a draft and for anything issued before PMS-959, and rendering a draft stores nothing. `Retention` on `ObjectKind` declares seven years for a financial document and while-referenced for everything else; nothing enforces it, there is no reaper, and a test fails the day a sweep appears in that module so the declaration cannot quietly become a promise.
- An invoice line names the work and the document addresses the customer (PMS-1004): `billing::descriptions::time_entry_line` is the one composer of a time-entry line's description (`{date} {work type}: {ticket number} {ticket title} - {notes}`), because the `Time entry {uuid}` the builder wrote before reached the API, the page and the PDF alike. `documents::BillTo` (the company's billing address, else its postal address, plus the billing contact) is resolved by `BillingService::bill_to` beside the issuer and handed to every document (PMS-1001 added `credit_to` and `statement_account` beside it, which differ only in where they source the contact); it is deliberately NOT frozen the way the issuer is, because PMS-959 keeps the bytes that were sent and a live render only serves a draft or a pre-PMS-959 document. `crate::pdf` gained `Document::columns`, `table_aligned` with a per-column `Align`, and `totals`; all deterministic, which `rendering_is_deterministic` and `the_invoice_shapes_render_on_one_page_and_deterministically` pin. A narrow table column keeps its width when the row overflows, so an amount is never cut to make room for a description.
- A document names the person it was sent to (PMS-1001): `update_invoice` writes the recipient `resolve_invoice_recipient` picked onto `invoices.billing_contact_id` on the first transition to `sent`, before the render in the same transaction, so an invoice created naming nobody stops being emailed to a person and addressed to an organization. That fallback (the company's `default_billing_contact_id`) had never been written down, and no create path resolves it, so it was the ordinary case rather than the edge one. The three documents then differ in where the contact comes from, deliberately: an invoice reads its OWN column, a credit note reads the column of the invoice it corrects, and a statement reads the company's CURRENT `default_billing_contact_id` (`BillingService::credit_to` and `statement_account` beside `bill_to`). The first two are historical because a reprint must name who received the document, and the statement is not because PMS-954 made it a read model that stores nothing and renders from today, the same rule its issuer and branding already follow. Documents already stored under PMS-959 are NOT re-rendered, so only invoices sent and credit notes created after this carry the block; `docs/invoice-lifecycle.md` says so, and `tests/document_bill_to.rs` reads the text back out of the served bytes rather than asserting on what the service passed around.
- A document prints the customer's own name (PMS-1007): `crate::pdf` embeds Noto Sans regular and bold, vendored in `src/pdf/fonts` with the SIL Open Font License 1.1 they ship under, instead of drawing with a base-14 `BuiltinFont`. A base-14 font is `WinAnsiEncoding`, so every code point above U+00FF became `?`: Latin Extended (`Łukasiewicz`), Greek, Cyrillic and the euro sign were all mangled on an invoice the customer keeps, while Latin-1 accents survived and hid it. Inside `src/pdf` and not a top-level `assets/`, because `oci-build/Dockerfile` already copies `src/` and `compose.dev.yml` already mounts it, and the licence is copied separately into the image since the font bytes themselves are compiled into the binary. Two costs are deliberate. printpdf subsets only behind its `text_layout` feature, which pulls a layout engine and system font discovery in, so the whole face is embedded and a rendered document grew from about 8 KB to about 460 KB - PMS-1008 owns shrinking that. And Noto Sans stops at its own coverage, chiefly CJK, so such a character is still `?`, but `render` now emits exactly one `warn` naming the characters and the document, because the substitution being SILENT is what made this reach a customer at all.
- Releases: `just create-release <major|minor|hotfix>` bumps `Cargo.toml`, pushes a `release/v<X.Y.Z>` branch, opens the PR. CI tags + publishes on merge.
- Email backend selection: `MailerConfig::from_env().build()` returns `SmtpMailer` if `SMTP_HOST` is set, `LogMailer` otherwise. `SMTP_USERNAME` without `SMTP_PASSWORD` is a hard error at startup (fail-loud, not silent degrade).
- `ENCRYPTION_KEY` must parse as 32 bytes (raw or 64 hex chars) via `utils::crypto::parse_encryption_key`. Used for AES-256-GCM at-rest encryption of per-tenant secrets (e.g. payment-gateway configs).
- `CORS_ORIGIN` is comma-separated; required to be a valid header value or startup panics. Defaults to `[CLIENT_ORIGIN]`.
- `LOGIN_APPROVAL_ENABLED` (PMS-658) turns on the suspicious-login notify-and-approve gate; off by default because it can withhold a login, so it is opt-in per deployment for a staged rollout. When on and a password login clears password/MFA but comes from a new country (needs `IP2LOCATION_DB_PATH`) or a new device (client-supplied `device_id` in the login body), the session/tokens are withheld and a single-use 6-digit code is emailed; the client re-POSTs `/auth/login` with `approval_code` to finish (mirrors the `mfa_required` flow). Off = the PMS-657 alert-only behaviour. Gates password login in v1 (the portal path is a follow-up); tables `login_approvals` + `user_login_devices`.
- Outbound-URL screening (PMS-805, PMS-809): every outbound fetch whose URL comes from a request or from tenant-editable configuration runs through `utils::net::guard_outbound_url`, which resolves the host and refuses any address `is_non_public_ip` rejects, before the first connect and again on every redirect hop. Three callers: the company website probe (`modules/contacts/website_probe.rs`, ports pinned to 80/443), the ticket-automation `webhook` action (`modules/tickets/automation.rs`, refusal logged with the rule id and the blocked address), and `TacticalRmmProvider` (`modules/rmm/provider.rs`, refusal is an `AppError::Configuration` surfaced in `rmm_connections.last_error`; redirects are not followed). Do not copy the predicate or the resolve loop: a second definition of either fails `utils::net`'s `exactly_one_definition_in_the_crate` test. `OUTBOUND_PRIVATE_ALLOWLIST` is the operator escape hatch (comma-separated hostnames, IPs, or CIDRs) for a self-hosted integration that really does live on a private network; unset means no exemption. Fetches whose URL comes from operator env are deliberately NOT screened (`INFISICAL_ADDRESS`, the Stripe API base, the `OIDC_ISSUER` JWKS, the fixed upstream version check).
- Client repository name (PMS-856): the SPA repository is `mokosh-apps`, and the name it replaced resolves to nothing. `repo_hygiene::the_former_client_repo_name_stays_gone` in `src/lib.rs` scans the working tree under `cargo test --lib` (a `check.yml` step) and fails if the old name reappears anywhere, so no new script, recipe or CI step carries the ban.
- Docker resource naming: every service/volume/network is prefixed with the app name; dev resources get an extra `dev-` prefix. Sub-service data stores sort adjacent to their parent (`dev-backup-infisical-postgres`, not `dev-backup-postgres-infisical`).
- Dev stack binds to a private LAN IP (br0/eth0), not 127.0.0.1, so sibling containers on the host can reach the API while the public internet cannot.
